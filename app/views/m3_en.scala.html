1. The Fab Challenge: Why the Salary-Savings Architecture Applies Directly

The salary-savings business chain (file gen → SFTP upload → poll response → parse → classify → route) is fundamentally a cross-system process orchestration problem. Semiconductor Fab manufacturing is the same — only the "external system" changes from a bank to equipment and MES, and the "file" becomes a FOUP/Lot.

4. M3-Specific: Three New Capabilities

These three capabilities handle Fab-specific physical constraints and dynamic routing. Each is an incremental addition on top of existing components — no existing code is modified.

🗺️

ProductRouting · Dynamic Process Routes

Step sequences are loaded from a database, not hard-coded. LOGIC-28NM-A uses an 11-step route (with Lithography reentry × 2); NAND-96L-A uses 13 steps (with Deposition/Etch cycles × 4). Process changes require a database update only — zero code changes.

fab/model/ProductRouting.scala · RoutingStep + ProductRouting
📦

BatchMergeManager · Lot Merge at Stock

A Lot (25 wafers) may be split during processing — some wafers rework to another area, some are scrapped. At stock-in, the system tracks original Lot ownership and auto-triggers merge when all surviving wafers complete. This physical constraint doesn't exist in salary-savings.

fab/orchestration/BatchMergeManager.scala · WaitForOthers / ReadyToMerge / PartialMerge
🔄

Reentry Tracking

An equipment area can be visited multiple times (Litho multi-patterning, 3D NAND Dep/Etch cycles). reentryIndex tracks the visit count, ensuring the correct recipe and equipment state for each visit. This is the core distinction from unidirectional flows.

fab/model/EquipmentArea.scala · reentryIndex calculation

5. FabFlowEngine: The Dynamic Assembly Engine

FabFlowEngine is the M3 core orchestrator — it reads ProductRouting, dynamically assembles a SubBatchPipeline for each step, batches by PhysicalConstraints, processes, classifies results, routes failures, and advances successes to the next step.

// FabFlowEngine core loop (simplified) def executeStep(lot: LotContext, step: RoutingStep): Future[LotContext] = { for { // 1. Dynamically assemble Pipeline for current equipment area pipeline <- resolvePipeline(step.areaId, lot.recipeId) // 2. Batch by physical constraints (FOUP 25, recipe-compatible) batches <- areaScheduler(step.areaId).schedule(lot.wafers) // 3. Process each sub-batch through SubBatchProcessor results <- Future.traverse(batches)(processor.process) // 4. Metrology 3-way split + borderline reconfirm resolved <- classifyAndReconfirm(results, step.areaId) // 5. Route failures: rework / switch area / scrap _ <- routeFailures(resolved.failures, lot.context) // 6. Advance successes to next step (with reentryIndex increment) advanced <- advanceToNextStep(resolved.successes, lot.routing) } yield advanced }
Proof of incremental evolution: In the code above, resolvePipeline calls M2.5+'s ChainTemplates.equipmentArea(), processor.process is M2.5+'s SubBatchProcessor, classifyAndReconfirm is M2.5+'s ResultClassifier + ReconfirmHandler, routeFailures is M2.5+'s ReBatchRouter. No M2.5+ component is modified — they are simply called in new sequences and conditions by FabFlowEngine.

Architect's perspective — why no new execution engine is needed. M2.5+'s business step chains, technical component stacks, and scheduling routers already cover the complete lifecycle of process execution. M3 changes only the source of step sequences — from compile-time static configuration to runtime-loaded dynamic routing. SagaTransactionCoordinator needs no changes; StepExecutor's circuit breaker / retry / timeout need no changes; Connector needs no changes. The only additions are ProductRouting (data model) + BatchMergeManager (Fab physical constraints) + FabFlowEngine (dynamic assembly). All new code is ~500 lines — compared to M2's 23 FSMs (~6000 lines of Java), that's a 12:1 compression ratio, while gaining dynamic process orchestration.
