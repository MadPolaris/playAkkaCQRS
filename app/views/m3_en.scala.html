1. From "Rail Transit" to "Autonomous Driving"

Traditional MES (the M2 era) resembles rail transit: process routes are dead rails laid out in advance. When the physical world deviates (e.g., Wafer 5 exceeds granularity spec), the system stalls, waiting for a human to throw the switch. M3 architecture transforms production logic into autonomous driving—with the Manufacture Unit (MU) at its core, treating every processing step as a "transaction," using dynamic routing and distributed transaction protocols to achieve a perfect mapping of physical facts into the digital world.

The core paradigm shift: M3's essence is preserving "the projection of physical facts in the information system without distortion." No matter how many splits and merges occur, the total MU asset count in the system must remain conserved. This consistency is not a simple database constraint—it's an information-theoretic, monotonically increasing fact repository.

2. The Account-Based Manufacture Unit (MU) Matrix

In M3, wafers are no longer passive objects—they are abstracted as "account-side participants." M3 decouples manufacturing objects by granularity, forming nested lifecycle management. The MU Matrix is viewed along two axes: the horizontal axis records all events on the timeline, the vertical axis drills through three granularity levels.

📦

Lot (Container Layer / FOUP)

The logical orchestration unit. Manages carrier position, physical transport, and WIP accounting. Every batching, split, and merge is recorded as an event on the horizontal timeline. Physically corresponds to a FOUP (25-wafer carrier)—the "logical container" for all Wafers.

💎

Wafer (Atomic Layer / Substrate)

The core fact carrier. Manages quality parameters, metrology facts, and yield tracking. Records every wafer's measurements, scratches, and which chamber it was processed in. Split is triggered by "fact anomaly"—Wafer 5 exceeds granularity spec → the system spawns two parallel timelines.

🎯

Die (Derived Layer / Chip)

The ultimate output value point. Exists as a Wafer attribute, recording the final Map facts. Data concentrates and erupts during CP (Chip Probe) and FT (Final Test) phases— each Die's electrical parameters, Bin classification, and yield decisions are recorded as critical facts at these stages.

The MU Matrix: Dual-Axis Structure

→ Horizontal: Timeline

Records all PhaseDone events from start to output. Every step completion, metrology result, split, and merge appends immutable fact records to the timeline. There isn't just one timeline—after a split, multiple parallel timelines grow simultaneously in the MU Matrix. At merge, BMM acts as a Barrier to align the timelines back into one.

↓ Vertical: Granularity Drill-Down

Lot Level—records FOUP transport, furnace batching records.
Wafer Level—records per-wafer measurements, scratches, chamber processing history.
Die Level—electrical Map facts during CP/FT test phases.
The relationship between levels is not foreign keys—it's an event sourcing projection. Any query at any level is a spatiotemporal slice of the Event Log.

Information-theoretic consistency: Saga in M3 evolves into the "guardian of fact conservation." It no longer manages fixed steps—it manages the atomicity of operations. Split is a cross-account transfer—ensuring parent debit and child creation happen atomically. Merge is a Barrier—only when each MU's progress is logically aligned, or forced into reconciliation via compensation protocol, does BMM sign the merge fact.

3. Three-Layer Architecture: Decision × Execution × Physical

M3 architecture completely decouples business logic from physical equipment through three-layer separation. The Decision Layer (M3 brain) figures out "what to do next," the Runtime Layer (M2.5+ muscle) "dispatches instructions with high throughput," and the Physical Execution Layer (Fab reality) performs "actual physical movement." The core objective: handle the extreme dynamism and uncertainty inherent in wafer fabrication.

POR → Dynamic Flow Assembler (Step Generator) → Saga/LotContext → ChainExecutionActor → StepExecutors → Equipment → ResultClassifier → Fact Logging Feedback Loop

The core value of three-layer separation: The Decision Layer only cares about "facts" and "protocols"—what happened in the physical world, what to do next. The Runtime Layer only cares about "execution"—how to reliably deliver commands to equipment and collect results with high throughput. The Physical Execution Layer only cares about "communication and precision"—how to translate SECS/GEM messages into domain events. Changes in any layer do not penetrate other layers—equipment upgrades don't affect business logic; process changes don't touch the execution engine.

5. Saga: Guardian of Fact Conservation

Saga undergoes a conceptual leap in M3—from M1's "distributed transaction coordinator" to "guardian of fact conservation." It no longer manages fixed step sequences, but the atomicity of operations and the conservation of information.

✂️

Split: Cross-Account Transfer

Split is essentially a cross-account transfer: parent Lot A debits Wafer 5–8, child Lot A' is created and receives these 4 wafers. Saga guarantees both steps happen atomically—either both succeed, or both roll back. The total MU asset count is always conserved: Lot A.count + Lot A'.count = original 25 wafers.

🔗

Merge: The Barrier

Merge is timeline unification. BMM watches parallel timelines—only when each MU's progress is logically aligned (all Wafers complete current process segment), or forced into reconciliation via compensation protocol (Scrap / Skip-to-merge-point), is the merge fact signed. Merge is not a physical operation—it's a logical barrier.

🛡️

Failure Recovery: SUSPENDED + ManualFix

When Compensate fails, Saga enters SUSPENDED state rather than deadlocking. Operators restore via ManualFixStep + RetryCurrentPhase. All intermediate states are written to Akka Persistence—no guessing "where we were stuck" during recovery.

Key difference from M1 Saga: M1's Saga manages fixed "Prepare/Commit/Compensate three-phase." M3's Saga manages "dynamically woven ChainDSL segments"—each DSL segment is self-contained with Prepare/Commit/Compensate semantics. Saga doesn't care what's inside a segment—it only cares whether the atomic boundary of the segment is guaranteed.

6. Exception Handling & Non-Linear Rollback

Given that wafer processing is physically irreversible (etched material doesn't grow back), M3 redefines "rollback." It's not a database ROLLBACK—the physical world has no CTRL+Z.

🔧

Physical Compensation: Inject Rework DSL

Non-conforming wafers aren't "rolled back"—they are rolled forward. The Dynamic Flow Assembler weaves a rework DSL and injects it into the execution engine. Example: litho pattern shift → strip resist → re-litho. Every step is a new physical operation consuming new resources.

📋

Logical Rollback: Saga Book Reconciliation

At the account operation level (e.g., split interrupted mid-way—parent debited but child not yet created), Saga performs logical rollback. Compensate reverse operations restore MU account balances, ensuring book data does not drift.

⚠️

Forced Merge: Entropy Convergence

In the normal state of "misalignment" (some Wafers scrapped, some still in rework), BMM uses strategies like forced scrap or skip-to-merge-point to achieve forced convergence from high-entropy state to low-entropy consistency.

Key insight: M3's exception handling is not try-catch—it's a protocol. Physical compensation looks forward—"since something went wrong, what can I do to fix it." Logical rollback looks backward—"book data must align with physical facts." These two work in concert to form M3's self-healing capability.

7. M2.5+ Execution Engine: M3's Muscle Layer

8. Architecture Motto & Code Reference

Architecture Motto: "Let the physical world determine the facts. Let the logical world manage consistency. Let dynamic routing drive the future."

M3 architecture builds a self-healing reactive kernel by account-izing Manufacture Units, protocol-izing Saga, and dynamizing process routes. It doesn't just answer "where am I" and "what did I do"—it solves "logical collapse caused by physical anomalies" at the foundational protocol level. Under M3, every FOUP docking and door-open is a sacred physical asset transaction, permanently witnessed by a distributed digital ledger.

M3 code spans two layers: the Decision Layer prototype lives under app/net/imadz/fab/; the production-quality Lot Context Saga follows the standard DDD package structure (domain/entities/, application/aggregates/, infrastructure/) and uses event sourcing with Akka Persistence — the same InvariantRule + CommandHelper + SagaParticipant pattern proven in M1 CreditBalance/MoneyTransfer.

Architect's perspective—why M3 is not a new engine. M3 doesn't start from scratch outside M2.5+. It adds a decision capability on top of M2.5+. Dynamic Flow Assembler doesn't replace ChainExecutionActor—it injects commands into ChainExecutionActor. Lot Context doesn't replace Saga—it enables Saga to manage more complex entity relationships. It's like an autonomous driving system not replacing the engine—it just tells the engine where to go.
