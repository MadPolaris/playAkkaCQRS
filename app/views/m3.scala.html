一、从"轨道交通"到"自动驾驶"

传统 MES（M2 时代）类似于轨道交通：工艺路线是预先铺设好的死铁轨。 一旦物理世界发生异常（如晶圆 5 颗粒度超标），系统往往陷入停滞，依赖人工拨动道岔。 M3 架构则将生产逻辑转变为自动驾驶——以制造单元（Manufacture Unit, MU）为核心， 将每一次加工看作是一笔"交易"，利用动态路由和分布式事务协议，实现物理事实在数字世界的完美映射。

维度M2 时代（轨道交通）M3 时代（自动驾驶）
工艺路线静态 List[Step]，编译时确定Step Generator——每道工序完成后根据 LotContext 事实动态计算下一段 DSL
实体模型Lot 是文件批次，Wafer 是行记录MU 账户矩阵——Lot/Wafer/Die 三级颗粒度，水平时间线 + 垂直穿透
异常处理停线等待人工介入Result Classifier 四路分流 → 物理补偿（返修 DSL）或逻辑撤销（Saga）
拆批/合批手动拆分、手动合并跨账户转账——Saga 保证父批次扣减与子批次创建原子发生
状态一致性数据库事务 + 外键约束信息论范畴——状态单调递增事实库，回放 Event Log 即可恢复与物理世界对齐的状态
路径来源流程工程师预先绘制Dynamic Flow Assembler——根据 Result Classifier 反馈"见招拆招"实时织造
核心范式转换：M3 的本质是维护"物理事实在信息系统中的投影不发生畸变"。 无论发生多少次拆批、合批，系统中 MU 的资产总量必须守恒。这种一致性不是简单的数据库约束，而是基于信息论的状态单调递增事实库。

二、账户化的制造单元 (MU) 矩阵

在 M3 架构中，晶圆不再是冰冷的被动对象，而是被抽象为"账户侧的角色（Participant）"。 M3 将制造对象进行颗粒度解耦，形成嵌套的生命周期管理。 MU 矩阵从两个维度看：水平轴记录时间线上的所有事件，垂直轴穿透三级颗粒度。

📦

Lot（容器层 / FOUP）

逻辑编排单元。负责载具位置、物理搬运及 WIP 核算。 每次成批、拆批、合批均作为事件记录在水平时间线上。 物理上与 FOUP（25 片载具）对应，是所有 Wafer 的"逻辑容器"。

💎

Wafer（原子层 / 晶圆）

核心事实载体。负责质量参数、量测事实及良率追踪。 记录每一片晶圆的量测数值、是否被划伤、在哪个腔体（Chamber）加工。 拆批的起因是"事实异常"——Wafer 5 颗粒度超标，系统生成两条并行时间线。

🎯

Die（衍底层 / 晶粒）

最终产出价值点。作为 Wafer 的属性存在，记录最终的 Map 事实。 数据集中在 CP 测试（晶圆针测）和 FT 最终测试阶段集中爆发—— 此时每个 Die 的电性参数、Bin 分类、良率判定作为关键事实入账。

MU 矩阵的双轴结构

→ 水平轴：时间线

记录从投料到产出的所有 PhaseDone 事件。 每一道工序完成、每一次量测结果、每一次拆批/合批，均在时间线上追加不可篡改的事实记录。 时间线不是一条——拆批后，MU 矩阵中多条并行时间线同时生长。 合批时，BMM 作为 Barrier 对齐各时间线，归一为一条。

↓ 垂直轴：颗粒度穿透

Lot 级别——记录 FOUP 搬运、进炉管（Batching）记录。
Wafer 级别——记录每一片晶圆的量测数值、划伤、腔体加工记录。
Die 级别——CP/FT 测试阶段的电性 Map 事实。
三个级别间的关系不是外键，而是事件溯源投影——任何级别的查询都是对 Event Log 的时空切片。

信息论一致性：Saga 在 M3 中演变为"事实守恒的守护者"。它不再管理固定的步骤，而是管理操作的原子性。 拆批是"跨账户转账"——确保父批次扣减与子批次创建原子发生。合批是"Barrier 屏障"——只有当各 MU 的进度在逻辑上对齐， 或通过补偿协议强制平账后，才签署合批事实。

三、三层架构全景：决策 × 执行 × 物理

M3 架构通过三层分离将业务逻辑与物理设备彻底解耦。 决策层（M3 大脑）负责"想清楚下一步该干什么"，运行时层（M2.5+ 肌肉）负责"高性能地分发指令"， 物理执行层（Fab 现实世界）负责"真正的物理位移"。 核心目标是处理晶圆生产中极高的动态性和不确定性。

POR → Dynamic Flow Assembler (Step Generator) → Saga/LotContext → ChainExecutionActor → StepExecutors → Equipment → ResultClassifier → 事实入账反馈闭环

五、Saga：事实守恒的守护者

Saga 在 M3 中经历了概念跃迁——从 M1 的"分布式事务协调器"演变为"事实守恒的守护者"。 它不再管理固定的步骤序列，而是管理操作的原子性和信息的守恒性。

✂️

Split 拆批：跨账户转账

拆批的本质是一次跨账户转账：父批次（Lot A）扣减 Wafer 5–8，子批次（Lot A'）创建并接收这 4 片 Wafer。 Saga 保证两步原子发生——要么同时成功，要么同时回滚。 系统中 MU 的资产总量始终守恒：Lot A.count + Lot A'.count = 原始 25 片。

🔗

Merge 合批：Barrier 屏障

合批是多时间线归一。BMM 盯着并行时间线——只有当各 MU 的进度在逻辑上对齐（所有 Wafer 完成当前工序段）， 或通过补偿协议强制平账（Scrap 报废 / Skip 跳步），合批事实才被签署。 合批不是物理操作，是逻辑屏障。

🛡️

故障恢复：SUSPENDED + ManualFix

当 Compensate（补偿）失败时，Saga 进入 SUSPENDED 状态而非死锁。 操作员通过 ManualFixStep + RetryCurrentPhase 恢复。 所有中间状态写入 Akka Persistence——恢复时无需猜测"当时卡在哪里"。

与 M1 Saga 的关键差异：M1 的 Saga 管理"固定的 Prepare/Commit/Compensate 三阶段"。 M3 的 Saga 管理"动态织造的 ChainDSL"——每个 DSL 片段自包含 Prepare/Commit/Compensate 语义， Saga 不关心片段内部是什么，只关心片段的原子边界是否得到保证。

六、异常处理与非线性回滚

在晶圆加工物理不可逆的前提下（刻蚀掉的材料不会长回来），M3 重新定义了"回滚"。 它不是数据库的 ROLLBACK——物理世界没有 CTRL+Z。

🔧

物理补偿：注入返修 DSL

不合格的晶圆不是"回退"，而是向前回滚——Dynamic Flow Assembler 织造一段返修（Rework）DSL， 注入执行引擎。例如：光刻图形偏移 → 去胶 → 重新光刻。每一步都是新的物理操作，消耗新的资源。

📋

逻辑撤销：Saga 账面回滚

在账户操作层面（如拆批中途宕机——父批次已扣减但子批次未创建），Saga 负责执行逻辑回滚。 通过 Compensate 反向操作恢复 MU 账户余额，确保账面数据不发生漂移。

⚠️

容错合批：强制收敛

在"对不齐"的常态下（部分 Wafer 报废、部分仍在重工），BMM 通过强制报废（Scrap）、 跳步对齐（Skip to merge point）等策略，实现高熵状态向低熵一致性的强制收敛。

关键洞察：M3 的异常处理不是 try-catch，而是协议。物理补偿是向前看的——"既然做坏了，我做点什么来补救"。 逻辑撤销是向后看的——"账面数据必须和物理事实对齐"。这两者协同，构成了 M3 的自愈能力。

七、M2.5+ 执行引擎：M3 的肌肉层

M3 的决策层（大脑）依赖 M2.5+ 的运行时组件（肌肉）来执行物理指令。 M2.5+ 的三层分离架构——业务维度（步骤链）、技术维度（通信/容错/编解码）、调度维度（分流/补偿）——全部无需修改， 直接作为 M3 运行时执行层的标准组件库使用。

八、架构格言与代码参考

架构格言："让物理世界决定事实，让逻辑世界管理一致，让动态路由驱动未来。"

M3 架构通过将 Manufacture Unit 账户化、将 Saga 协议化、将 工艺路线 动态化， 构建了一个具备自愈能力的反应式内核。它不仅解决了"我在哪"和"我做了什么"的问题，更从底层协议层面解决了"由于物理意外导致的逻辑崩塌"。 在 M3 架构下，每一个 FOUP 的停靠与开门，都是一笔神圣的物理资产交易，由分布式的数字账本永久见证。

M3 代码分布在两个层面：决策层原型位于 app/net/imadz/fab/ 包； 生产级 Lot Context Saga 遵循标准 DDD 包结构 （domain/entities/、application/aggregates/、infrastructure/）， 使用 Akka Persistence 事件溯源——与 M1 CreditBalance/MoneyTransfer 采用完全相同的 InvariantRule + CommandHelper + SagaParticipant 模式。

架构师视角——M3 为什么不是一个新引擎。 M3 不是在 M2.5+ 之外另起炉灶。它是在 M2.5+ 之上增加了一层决策能力。 Dynamic Flow Assembler 不替代 ChainExecutionActor——它向 ChainExecutionActor 注入指令。 Lot Context 不替代 Saga——它让 Saga 管理更复杂的实体关系。 这就像自动驾驶系统不替代发动机——它只是让发动机知道该往哪开。 代码压缩比：M2 的 23 个 FSM（~6000 行 Java）→ M2.5+ 的 16 个运行时组件（~2000 行 Scala）→ M3 决策层 （~500 行原型 + ~2500 行生产级 Lot Context Saga，含事件溯源和 TCC 分布式事务）， 同时获得了动态工序编排能力。

九、M3.5 · 自愈决策内核 — 从静态脚本到反应式内核

M3.5 在 M3 决策层之上增加了崩溃自愈和OCAP 拦截能力。 它回答了一个关键问题：当执行引擎本身崩溃时，工单如何不卡死？

单 WorkOrder 自愈：EventSourced 断点恢复

每个 WorkOrder 对应一个 FabPipelineExecutionActor（EventSourcedBehavior）。 其状态机包含四个状态：Idle → Executing → Completed / Failed。 Pipeline 执行过程中，每完成一个阶段（Phase），就持久化一条 PhaseCompleted 事件， 将阶段名称追加到 completedPhases 游标中。

💾

EventSourced 持久化

所有 PhaseCompleted 事件写入 Akka Persistence Journal（MongoDB）。 崩溃后 Actor 重启，事件重放恢复 completedPhases 游标。 系统知道自己"跑到哪了"，不会丢失进度。

⏭️

断点续传 resumeFromIndex

RecoveryCompleted 信号中重建执行上下文， 调用 FabPipelineProcessor.resumeFromIndex(state, completedCount)—— 跳过已完成阶段，从中断处继续执行后续阶段。

🛡️

OCAP 故障拦截

Pipeline Stage 执行失败时，FabScenarioPipeline.invokeOcapInterceptor 匹配 OCAP 规则（条件评估 + 优先级排序），执行 Rework / Scrap / Hold / Notify / AdjustRecipe 动作。 规则从 HOCON 配置文件热加载，无需重启。

当前能力边界

已实现：单 WorkOrder 中途崩溃 → EventSourced 状态恢复 → 断点续传 → OCAP 故障拦截。 在 Executing 状态下崩溃，Pipeline 可从已完成阶段后自动恢复。
已知边界：若崩溃在 Idle 状态命中（StartExecution 尚未处理）， fire-and-forget 消息丢失后缺少上层编排聚合重试。多 WorkOrder 并发场景下， 尚无 WorkOrderBatch 聚合或 Watchdog 机制保证所有工单最终启动。 这是 M3.5 的后续攻坚方向。
