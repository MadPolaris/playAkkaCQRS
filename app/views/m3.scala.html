一、Fab 的挑战：为什么薪资存入的架构可以直接用

薪资存入系统处理的业务链路（文件生成 → SFTP 上传 → 轮询回盘 → 解析 → 分类 → 分流）本质上是一个跨系统工序编排问题。 Fab 半导体制造也是——只是"外部系统"从银行换成了机台和 MES，"文件"换成了FOUP/Lot。

二、9+1 设备区

每个设备区在 M2.5+ 中对应一条独立的业务链路（ChainDefinition），拥有自己的 SubBatchPipeline 和 ErrorCodeMapping。 10 个设备区 = 10 条链路配置——每条 ~20 行 DSL，而非 10 个手写 Actor。

四、M3 特有：三个新增能力

这三个能力是 M2.5+ 没有的——它们处理 Fab 特有的物理约束和动态路由。每个都是增量叠加到现有组件之上，不修改已有代码。

🗺️

ProductRouting · 动态工艺路线

工序序列从数据库加载，而非硬编码在代码中。产品 LOGIC-28NM-A 走 11 道工序（含 Lithography 重入 2 次），NAND-96L-A 走 13 道（含 Deposition/Etch 4 次循环）。工艺变更时更新数据库即可，不需要改代码。

fab/model/ProductRouting.scala · RoutingStep + ProductRouting
📦

BatchMergeManager · 合批入库

原始 Lot（25 片）在加工过程中可能被拆散——部分片 rework 去了别的设备区、部分片报废。入库时，追踪原始 Lot 归属，所有合格片完成后自动触发合批。这是薪资存入系统不存在的物理约束。

fab/orchestration/BatchMergeManager.scala · WaitForOthers / ReadyToMerge / PartialMerge
🔄

Reentry Tracking · 重入追踪

同一设备区可能被访问多次（光刻的多重曝光、3D NAND 的沉积刻蚀循环）。reentryIndex 追踪第几次访问，确保每次使用正确的 recipe 和设备状态。这是 Fab 区别于单向流程的核心特征。

fab/model/EquipmentArea.scala · reentryIndex 计算

五、FabFlowEngine：动态组装执行引擎

FabFlowEngine 是 M3 的核心编排器——它读取 ProductRouting，为每一步动态组装 SubBatchPipeline， 按 PhysicalConstraints 成批，执行处理，分类结果，分流失败项，推进成功项到下一道工序。

// FabFlowEngine 的核心循环（简化） def executeStep(lot: LotContext, step: RoutingStep): Future[LotContext] = { for { // 1. 为当前设备区动态组装 Pipeline pipeline <- resolvePipeline(step.areaId, lot.recipeId) // 2. 按物理约束成批（FOUP 25 片、同 recipe 兼容） batches <- areaScheduler(step.areaId).schedule(lot.wafers) // 3. 每个子批次通过 SubBatchProcessor 执行 results <- Future.traverse(batches)(processor.process) // 4. 量测值三路分流 + 可疑值复核 resolved <- classifyAndReconfirm(results, step.areaId) // 5. 失败项路由：rework / 换区 / 报废 _ <- routeFailures(resolved.failures, lot.context) // 6. 成功项推进到下一道工序（含重入索引递增） advanced <- advanceToNextStep(resolved.successes, lot.routing) } yield advanced }
渐进演进的核心证明：上面的代码中，resolvePipeline 调用的是 M2.5+ 的 ChainTemplates.equipmentArea()， processor.process 是 M2.5+ 的 SubBatchProcessor， classifyAndReconfirm 是 M2.5+ 的 ResultClassifier + ReconfirmHandler， routeFailures 是 M2.5+ 的 ReBatchRouter。 没有任何一个 M2.5+ 组件被修改——它们只是被 FabFlowEngine 以新的顺序和条件调用。

架构师视角——为什么不需要新的执行引擎。 M2.5+ 的业务步骤链、技术组件栈、调度分流器已经覆盖了"工序执行的完整生命周期"。 M3 的变化在工序序列的来源——从编译时确定的静态配置变为运行时加载的动态工艺路线。 SagaTransactionCoordinator 不需要改动；StepExecutor 的断路器/重试/超时不需要改动；Connector 不需要改动。 唯一新增的是 ProductRouting（数据模型）+ BatchMergeManager（Fab 物理约束）+ FabFlowEngine（动态组装）。 所有新增代码约 500 行——对比 M2 的 23 个 FSM（~6000 行 Java），这是 12:1 的代码压缩比，同时获得了动态工序编排能力。
