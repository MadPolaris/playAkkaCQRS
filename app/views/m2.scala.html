一、为什么需要 DAG 执行引擎

M1 Saga 解决了单个分布式事务的原子性问题。但在真实业务场景中， 一个操作往往涉及多个外部系统的长链路编排——定时触发、文件生成、SFTP 上传、 轮询结果、分类处理、异常路由、通知下游——这不是一个简单的请求-响应能覆盖的。 M2 DAG 执行引擎将跨系统流程建模为有向无环图（DAG），每个节点是一个独立的 Persistent FSM， 边代表数据流和依赖关系。

维度传统存储过程编排M2 DAG 执行引擎
流程定义JSON → 存储过程调用链，运行时不可见显式 DAG——节点和边在代码中声明，编译时检查
节点独立性存储过程间隐式依赖，一处失败全局回滚每个 FSM 独立持久化、测试、部署——爆炸半径限制在单个节点
外部系统集成DB Link、批量 ETL、轮询统一通信层——SFTP/HTTP/消息队列，封装在可重试的异步边界内
弹性模式无——失败靠人工4 种内建模式：监督重启、超时保护、补偿恢复、最终一致
流批一体流式和批量两套系统，逻辑重复同一套 DAG 管道同时处理实时事件和批量文件
可观测性日志文件 grep每个 FSM 的状态转换作为事件持久化——click→drill→debug
薪资存入场景：M2 的 Demonstrator 是一个发薪日薪资自动存入流程——定时触发 → 数据预处理（生成文件 / 上传 SFTP / 轮询响应 / 解析 / 分类）→ 额度预留 → 并发执行（充值 + 申购两条并行链路）→ 补偿收尾。涉及 4 个外部系统（银行 SFTP、核心账户 API、基金申购平台 P2B、短信通道），23 个 FSM 协同完成。

二、5 层级 DAG 架构全景

M2 将跨系统编排拆分为 5 个垂直层级，每层有明确的职责边界。层级之间的数据流是单向的—— 上层向下传递指令，下层向上反馈结果。异常通过补偿回路回到上层。

L0 触发层 → L1 编排层 → L2 执行与资源层 → L3 业务链路层 → L4 通信层 → L5 补偿释放层

层级职责速览

层级弹性角色包含 Actor核心职责
L0 触发层编排器Quartz Cron 调度器 (1 个)定时触发作业——DAG 由事件激活，不是存储过程调用链
L1 编排层编排器 + 补偿器JobActor · PreBatchActor · ReBatchActor (3 个)作业拆分、批次管理、失败补偿——ReBatchActor 死循环重试直到成功
L2 执行与资源层编排器 + 保护器BatchMaster · BatchItemCreationActor · BatchWorker×N · UserQuotaReservation · QuotaRelease×2 (6 个)批量创建、并发执行、额度锁——保护器声明不变量，引擎强制执行
L3 业务链路层通信器充值链 + 申购链 (各 6 个 FSM，共 12 个)Request → Response → Reconfirm → Success/Failure → Notify——双链路并行
L4 通信层通信器 + 辅助SftpService · CoreAccountAPI · P2B Platform · SMS 通道 (4 个网关)异构外部系统封装——SFTP/HTTP/SMS，可重试异步边界
L5 补偿释放层保护器用户额度释放 + 总额度释放 (2 个)无论成功失败，保证资源最终释放——不掉锁

三、4 种弹性模式

M2 的 23 个 FSM 内建了 4 种弹性模式。这不是事后贴上的 try-catch——每个 FSM 的类型本身就是一种弹性策略。

🎯

Orchestrator 编排器

负责作业拆分、批次管理和阶段推进。每完成一个阶段，持续检查下一个阶段的前置条件。 如果子节点失败，Orchestrator 决定是重试还是启动补偿链。 对应 Actor：JobActor、PreBatchActor、BatchMaster。

🛡️

Protector 保护器

声明系统不变量，并由引擎强制执行。例如："锁在 30 秒后自动释放"—— 即便节点崩溃，恢复后计时器仍会触发释放。保护器不是 try-finally，它是不变量的持久化守卫。 对应 Actor：UserQuotaReservation、QuotaRelease。

📡

Communicator 通信器

封装与外部系统的所有交互。将 SFTP 上传、HTTP 请求、轮询响应统一建模为异步消息。 外部不确定性被隔离在可重试的边界内。断路器保护下游系统。 对应 Actor：L3 全部 12 个业务链路 FSM + L4 全部网关。

↩️

Compensator 补偿器

最终的兜底机制。只要补偿器在运行，就没有失败会被遗漏。 ReBatchActor 以死循环重试的方式确保最终成功——每次失败后自动重新排队。 补偿释放层保证所有被锁定的资源最终被释放。

为什么 4 种模式就够了：跨系统编排中的每一个参与者，其行为都可以归类为这 4 种角色之一。 编排器负责"推进"，保护器负责"守护"，通信器负责"对话"，补偿器负责"兜底"。 这 4 种模式的组合覆盖了从定时触发到最终资源释放的完整闭环。

四、流批一体管道

传统架构中，流式（实时消息）和批量（文件传输）需要两套独立的处理系统—— 不同的触发机制、不同的执行路径、不同的错误处理。M2 通过统一的 DAG 管道将两者合并。

📂

批量路径（Batch）

Cron 定时触发 → 生成文件 → SFTP 上传 → 轮询响应文件 → 解析 + 分类 → 逐条创建子批次 → 并发处理 → 结果汇总。适用于薪资日批量存入、对账文件处理。

⚡

流式路径（Streaming）

跳过文件生成和 SFTP——直接从消息队列/HTTP 接收事件 → 解析 + 分类 → 逐条创建子批次 → 并发处理 → 结果汇总。适用于实时交易、即时通知。

共用的核心：无论批量还是流式入口，L2 以下的执行管道完全一致—— BatchWorker 的并发处理、业务链路层的请求-响应-确认-通知模式、 补偿释放层的资源回收——全部复用，零重复代码。

五、从 M2 到 M2.5+：从手写 FSM 到标准组件

M2 证明了"跨系统 DAG 编排引擎"的可行性——23 个 Persistent FSM 协同完成了复杂的薪资存入场景。 但它也暴露了一个核心限制：每个业务场景需要手写 23 个 FSM。 从薪资存入到 Fab 设备通讯，尽管流程结构高度相似（文件生成→上传→轮询→解析→分类→路由）， 但每个场景需要重新编写全部 FSM。M2.5+ 将这些模式抽象为 6 个标准组件—— 修复一次，全局生效。

M2 手写 FSMM2.5+ 标准组件提升
PreBatchActor + BatchMaster + BatchItemCreationActor (编排器)AreaScheduler (Process Manager)物理约束成批 · 时间窗口 · 配置化而非代码
BatchWorker + 6 个协议 FSM (通信器)SubBatchProcessor (6 阶段 Future 链)fileGen→upload→waitAck→poll→parse→classify——可插拔特质
3 种硬编码错误分类ResultClassifier (ErrorCodeMapping)配置化错误码→分类映射——PASS/BORDERLINE/FAIL/SCRAP
ReBatchActor (补偿器)ReBatchRouter (PolicyBased)RetrySameArea / RouteToArea / Scrap / ManualIntervention
SftpService / CoreAccountAPI / P2B / SMSConnector + Codec (可插拔)SFTP→SECS/GEM · XML→JSON/SECS-II——只换连接器
QuotaReservation + QuotaRelease (保护器)ChainExecutionActor (EventSourced)4 个通用事件覆盖所有业务链路 · 自愈恢复 · 幂等执行
演进的核心证明：M2.5+ 用 16 个运行时组件（~2000 行 Scala）替代了 M2 的 23 个手写 FSM（~6000 行 Java）， 同时获得了跨业务场景复用能力。充值、申购、SMS 通知、Fab 设备通讯——同一套组件，只换配置。
