158 万行记录。
一个数据库事务。
一个 Lot 的 Start。

西门子 Opcenter EX CR 的高性能引擎（HPE）技术参考文档（2021 年 7 月） 记录了一个 Multi-Level Start 事务：在单个 Oracle 事务中写入了 1,580,003 条数据库记录——通过一连串存储过程（clfExecute、 clffunc*）在数据库中批量执行 SQL。其中绝大多数是审计追踪记录、 历史快照、交叉引用索引——属于下游工序需要的数据，而不是当前操作。 但因为数据库事务是唯一的一致性保证，所有数据被硬塞进一个原子写。

把这个场景投射到 2nm 工艺。 GAA 纳米片晶体管。每片晶圆 2000–3000+ 道工序（7nm 时代大约 1000 道）。 每个关键层都需要多重曝光。每一道工序都需要在线量测。 158 万行不是天花板——它只是起点。 在 2nm 节点，我们面对的是每个 Lot 事务 500 万到 1500 万行记录。 Oracle 和 DB2 能执行吗？技术上能。但是在锁住数十张表的同时？ 让机台在一边闲置等待？在事务执行到一半失败时——能在几秒内恢复，而不是几小时？

如果换一条路呢？ 一个开源的、追求 6 个 9 可靠性的反应式 MES 核心引擎。 用事件溯源取代巨型事务，用 Saga 取代存储过程， 用流批一体的 DAG 执行引擎编排跨系统流程。

里程碑 1 和 2 已完成上线。里程碑 3 和 4——我们希望与 Fab 行业的人一起定义。

以数据库为核心的架构死胡同

这不是虚构的稻草人。这是西门子/HPE 在半导体制造领域的真实案例。

1,580,003

条数据库记录，在单个 Oracle 事务中。一个 Multi-Level Lot Start。

机制：JSON 负载发送到存储过程（clfExecute、clffunc*）， 在数据库服务器上解析并批量执行 SQL——西门子称之为"高性能引擎"（HPE）， Opcenter EX CR 的一个单独授权功能。 存储过程逻辑无法单元测试、无法版本控制、无法水平扩展。

关键问题：这 158 万条记录中绝大多数不是当前操作需要的。 它们是历史表（HistoryMainline、StartHistoryDetail、HistoryCrossRef）、 当前状态快照、交叉引用索引、工序计数——为下游查询和审计需求而存在的数据。 但因为数据库事务是唯一的一致性保证，所有写入被锁在同一次原子操作中。 下游的数据压力被迁移到上游，Lot Start 慢到了最大批量插入的速度。

来源：Siemens Opcenter EX CR — Technical Reference: High Performance Engine, Release 8G.1 (July 2021)。

🔮 投射到 2nm GAA 工艺节点

158 万行的参考数据来自 7nm/5nm 时代（每片晶圆约 1000 道工序）。 到了 2nm——GAA 纳米片晶体管、高 NA EUV 光刻、2000–3000+ 道工序—— 每个 Lot 的 Container、历史记录、交叉引用数量会爆炸式增长。 保守估计：每个 Lot 事务 500 万–1500 万行记录。

Oracle 或 DB2 能执行 1500 万行的存储过程吗？技术上能。 但在锁住数十张表的同时？在机台闲置等待的同时？ 在事务执行到一半失败时——能在几秒内恢复，而不是几小时？ 到了 2nm，存储过程方案不仅仅是性能瓶颈—— 它会成为限制整个 Fab 吞吐量的天花板。

机台等待 = 产能损失

巨型事务持有锁期间，机台处于空闲等待状态。在 Fab 里，每分钟的机台闲置都是不可挽回的营收损失。

跨系统状态漂移

MES 显示晶圆在工序 47。EAP 显示工序 46。RMS 里根本没有记录。这些不一致悄无声息地导致错误派工和错误配方。

脆弱的故障恢复

一个 158 万行（2nm 时代 1000 万+ 行）的存储过程执行到一半失败，恢复全靠人工。数小时的停机。DBA 和操作员手动分析部分状态。没有自动补偿，没有部分进度保留。

2nm 时代的吞吐量天花板

月产 10 万片晶圆、每片 3000 道工序的 Fab 产生的并发事件远超当前 MES 负载。存储过程串行执行模型不伸缩——每个 Lot Start 都成为全局串行化点。

换一条路

问题的根源不是"数据库不够快"，而是一致性边界被划错了地方。 审计追踪记录、历史快照、交叉引用索引——它们不应该和当前操作放在同一个事务里。 跨系统的数据对齐不应该依赖数据库外键，而应该靠事件驱动的最终一致性。 流程编排不应该硬编码在 JSON 驱动的存储过程中，而应该是显式的、可测试的、可演进的 DAG（有向无环图）。

这在今天很重要。到了 2nm，它决定了 Fab 的吞吐量上限。

Fab 痛点反应式解法
158 万行巨型事务Saga 将事务拆为独立步骤，只锁定当前需要的数据。下游写入通过事件异步驱动，不阻塞当前流程。
跨系统状态不一致事件溯源提供不可篡改的完整审计日志。投影订阅事件流，各系统的读模型通过事件流保持最终一致。
机台等待数据就绪异步消息驱动消除同步阻塞。机台发信号即刻得到响应，后续处理在后台完成。
故障恢复靠人工Saga 自动补偿已完成的步骤，监督层级树自动重启失败的组件。已知故障模式无需人工介入。
峰值吞吐扩展集群分片将实体实例分布至多节点。水平扩展无单点瓶颈。每个聚合根独立处理自身事件。

反应式基石

《反应式宣言》 的四大支柱不是抽象原则——它们直接对应 Fab 控制系统的核心需求。 基于 Akka（反应式宣言作者 Jonas Bonér 创建的宣言参考实现）。

📨

消息驱动

异步消息传递是系统的骨架。松耦合和位置透明使每个子系统可以独立伸缩——EAP 信号、MES 状态变更、SPC 告警全部以消息形式流转。

Fab：机台信号作为消息到达，永不阻塞发送方
🛡️

韧性

故障被隔离在单个组件内部。监督层级树阻止故障传播——一个 EAP 连接失败不会级联导致整个 Fab 控制系统崩溃。

Fab：单台机台通信故障不拖垮 MES
📈

弹性

根据负载动态伸缩。集群分片将实体实例分布至多节点——新产线投产时，系统无缝吸收新负载，无需重新架构。

Fab：新增产线无需推倒重来
⚡

灵敏性

任何条件下都提供快速、一致的响应时间。非阻塞 I/O 和背压机制确保延迟可预测——这是 Fab 运营所依赖的即时反馈环。

Fab：机台派工在毫秒级响应，不是秒级

事件溯源 × CQRS

事件溯源和 CQRS 是驱动反应式 MES 内核的两个核心模式。 它们解决了数据库中心架构无法解决的问题。

事件溯源

系统状态通过重放不可变的事件日志来重建。每一次状态变更——机台分配、晶圆移动、配方执行——都被捕获为领域事件。完整的审计追踪、时间点查询（14:03:27 时状态是什么？）和可靠的调试能力。Akka Persistence 自动处理日志存储和快照。

CQRS — 读写分离

命令修改写端状态（事件溯源聚合根）。查询读取优化的投影（MySQL）。写端只追加事件，保持极速。读端可自由去规范化、索引和优化，每种查询模式独立调优。

实时投影

Akka Projections 将事件流转换为读模型表。每个投影订阅特定聚合类型的标签事件，事务性处理并更新 MySQL——提供最终一致性的查询视图，保证至少一次投递。

Saga 模式（TCC 分布式事务）

无需分布式锁的分布式事务。Try-Confirm/Cancel：每个步骤先预留资源（Prepare），然后确认提交或补偿取消。失败触发向后补偿——只补偿 Prepare 成功的步骤。挂起事务支持人工介入。

能力维度数据库中心（存储过程）事件溯源 + CQRS
审计追踪触发器手动记录，不完整每次状态变更是不可变事件——完整历史
读取性能被同一事务中的写操作竞争专用读模型，每种查询模式独立优化和伸缩
调试"下午2点的状态是什么？"——从备份猜测确定性重放事件到任意时间点
模式演进破坏性迁移，存储过程版本管理噩梦仅追加事件；上抛器无损处理模式演进
跨系统集成批量 ETL、轮询、跨库外键实时事件流；推送式投影保持所有系统对齐
故障恢复人工介入，小时级停机。2nm 规模（1000万+行），部分故障分析本身就需要数小时Saga 自动补偿 + 监督层级；已知故障模式自动恢复。每个步骤独立恢复
