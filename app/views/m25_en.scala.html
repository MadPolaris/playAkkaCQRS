2. M2.5+ Solution: Three-Dimension Separation Architecture

M2.5+ partitions the system into three orthogonal dimensions — Business defines step sequences & batch mgmt, Technical encapsulates protocol stack & fault tolerance, Scheduling standardizes result routing & exception handling. Each dimension evolves, tests, and fixes independently; combined they cover the complete cross-system orchestration lifecycle.

WO → Batch Mgr splits → Process Seq Mgr advances step → Business step chain executes → Tech components enable remote comm → Result Scatterer 3-way routing → Exception Schedule / Reconfirm

Three-Dimension Components

Business Dim · Process Management & Execution

📋
Batch Mgmt

Batch Manager

Splits work orders into batches, manages batch lifecycle. Each batch contains ×2000 manufacturing units, independently advancing through the business step sequence.

🔀
Step Advancer

Per-Batch Process Sequence Mgr

Manages current batch step, advances/rolls back the sequence. 5 standard step templates: ① Quota Reserve→② Batch Deposit→③ Batch Purchase→④ Batch Notification→⑤ Quota Release. Each step has 4 standard processes: Initiate→Collect→Scatter→Reconfirm (all async, event-driven).

Technical Dim · Standardized Reusable Components

📦
Physical Constraints

Outbound Buffer · Re-batch

Re-batches by physical constraints (FOUP capacity, time window, recipe compatibility) then dispatches to equipment. Salary scenario: loose constraints (1-100 items). Fab scenario: strict constraints (FOUP 25 wafers).

⚡
Fault Tolerance

Circuit Breaker

Built-in retry, timeout, trip, recovery. All external communication uniformly protected by circuit breaker — faults are isolated, not propagated.

🔄
Format

Codec

JSON/XML/CSV/encrypted file format conversion. Encoding strategy decoupled from connectors. New message formats only need to implement the Codec interface.

🔒
Security

Encryption

Transport TLS / application AES / SM4. Encryption strategy parameterized, auto-selected by external system security level.

🔌
Communication

Protocol Stack

SFTP/HTTP-XML/HTTP-JSON multi-protocol adaptation. New transport protocols only need to implement the Connector interface — no impact on upper business logic.

Scheduling Dim · Result Routing & Exception Handling

🎯
Routing

Batch Result Scatterer

Performs three-way routing on each unit result: ✅ Success → next business step; ❌ Failure → escalate to Exception Scheduler; ⚠️ Suspicious → send to Reconfirmation Component. All async, event-driven.

🚨
Exception

Exception Scheduler

Receives failure results from the Scatterer, applies buffer (space constraint) and timeout (event constraint), then sends forward compensation to Batch Manager to reassign the business step (compensate/skip/terminate).

🔍
Reconfirm

Reconfirmation Component

Performs secondary verification on suspicious results (via higher-precision metrology, Core API check, or manual review), determines final success/failure, then returns result to Scatterer. Not a mandatory pipeline stage — success and failure items bypass this.

Key Design Decision: Three-Dimension Separation vs Monolithic FSM. Business Dimension defines "what to do" (step sequences), Technical Dimension provides "how to do it" (communication/fault-tolerance/encryption), Scheduling Dimension decides "where results go" (success advance/failure compensate/suspicious reconfirm). Three-dimension separation means: business teams modify step sequences without touching tech components; infrastructure teams upgrade circuit breakers without understanding business logic; scheduling policy changes (e.g. "suspicious threshold from 5% to 3%") are parameter config, not code changes. Unlike M2 hand-written FSMs: components are instantiated at runtime by parameters — fix a bug once, all instances automatically inherit the fix.

3. Business Parameterization: Three Dimensions, Independent Configuration

The core value of M2.5+ is not "lines of code eliminated" but the blast radius of a change. Each dimension has independent parameters: Business dim configures step sequences & batch constraints, Technical dim configures protocol/retry/encryption, Scheduling dim configures routing rules & compensation strategies. Parameters that PMs care about are elevated from deep code to config layer — each dimension changes and validates independently.

M3 Exclusive: Three New Capabilities

🗺️

ProductRouting · Dynamic Process Routing

Process sequences loaded from database, not hard-coded. LOGIC-28NM-A may run 11 steps (with Lithography reentry), NAND-96L-A runs 13 (with Deposition/Etch 4 cycles). Process changes: update the database, no code changes needed.

📦

Original Lot (25 wafers) may be split during processing — some rework to other areas, some scrap. At stocker entry, track original Lot ownership, auto-trigger merge when all qualified wafers complete. This physical constraint differentiates Fab from salary deposit.

🔄

Reentry Tracking

Same equipment area may be visited multiple times (Lithography multi-patterning, 3D NAND dep-etch cycles). reentryIndex tracks visit count, ensures correct recipe and equipment state per visit.

Architect Perspective — Why no new execution engine is needed. M2.5+ business step chain, tech component stack, and scheduling router already cover the "complete process execution lifecycle." M3 change is in the source of process sequences — from compile-time static config to runtime-loaded dynamic routing. SagaTransactionCoordinator: no change. StepExecutor CB/retry/timeout: no change. Connector: no change. Only additions: ProductRouting (data model) + BatchMergeManager (Fab physical constraints) + FabFlowEngine (dynamic assembly).

7.6 Concrete Examples: M2 Business Messages in M2.5+ Equivalent Form

Three before/after comparisons showing how a complete M2 business flow's messages and events are carried with equal information content in M2.5+.

Ex 1: Starting a Recharge Request — M2 FSM to M2.5+ Pipeline Equivalent

M2's StartRechargeRequest → FileGenerating → FileGeneratedCompleted → FileUploading → ... is a full FSM transition chain. M2.5+ replaces it with a Future pipeline.

M2 Java — RechargeRequestActor (300+ line FSM)
// 300+ line FSM: query DB → generate CSV → compute MD5 → update status
case New:
  on StartRechargeRequest:
    List<SalarySavingItem> plans = db.queryValidItems(batchId);
    generateRechargeFile(plans);          // write .txt + .md5
    updateBatchStatus(FileGenerating);
    tell self FileGeneratedCompleted;     // trigger next state
    → state = FileGenerating

// FileGenerating → FileUploading:
case FileGenerating:
  on FileGeneratedCompleted:
    updateBatchStatus(FileGenerated);
    tell self RequestUploadFile;
    → state = FileUploading

// FileUploading → FileUploaded:
  tells SftpService SftpCommand.UploadFile(path, remotePath)
  on SftpCommand.FileUploadComplete:
    updateRemoteFilePath(remotePath);
    → state = FileUploaded

// ↑ each transition = command → event → side-effect → new state
M2.5+ Scala — SubBatchProcessor (no FSM internally)
// SubBatchProcessor uses Future chains internally:
val processor = new SubBatchProcessor[Item, Raw](pipeline)

// 6-stage Future chain:
def process(batch: SubBatch[Item]) =
  for {
    file  <- pipeline.fileGen.generate(items, ctx)
    // ≡ StartRechargeRequest → FileGenerating → FileGeneratedCompleted
    rcpt  <- pipeline.upload.upload(file, ctx)
    // ≡ RequestUploadFile → SftpCommand.UploadFile → FileUploadComplete
    ack   <- pipeline.waitAck.waitForAck(rcpt, ctx)
    // ≡ RequestNotifyEams → EamsNotifyCreated
    resp  <- pipeline.pollResp.poll(ctx)
    raw   <- pipeline.parse.parse(resp, ctx)
    cls   <- pipeline.classify.classify(raw, batch.items)
  } yield SubBatchResult(cls)

// No explicit state inside the pipeline — phases connect via type changes
// Event Sourcing & state recovery provided by outer ChainExecutionActor (see Section 8)

M2's RechargeResponseActor.rechargeResponseFile() with AwaitResultRequested(items) event containing classified results. M2.5+ uses ErrorCodeMapping.

Ex 3: Failure Routing — From Hard-coded Retry Logic to Policy Configuration

M2's ReBatchActor + BatchWorker hard-codes retry logic. M2.5+ uses ReBatchPolicy.

M2 Java — ReBatchActor + BatchWorker
// ReBatchActor hard-coded retry:
if (retryCount > 3) {
  sendManualInterventionAlert(item);   // manual intervention
} else {
  scheduler.schedule(
    () → worker.tell(RetryItem(item)),
    5, TimeUnit.MINUTES
  );                                   // retry after 5 min
}

// Problems:
// 1. Retry count (3) & wait time (5min) are hard-coded
// 2. All failures retry uniformly; can't distinguish causes
// 3. Recharge/Purchase each have a ReBatchActor with nearly identical code
M2.5+ Scala — PolicyBasedReBatchRouter
// Policy configuration — replaceable at runtime without touching engine
val policy = ReBatchPolicy(
  maxRetries = 3,
  actionMap = Map(
    "BALANCE_INSUFFICIENT" → NextStep.Scrap,
    "QUOTA_EXCEEDED"       → NextStep.Scrap,
    "TIMEOUT"              → NextStep.RetrySameArea(5.minutes),
    "NETWORK_ERROR"        → NextStep.RetrySameArea(30.seconds)
  ),
  defaultCooldown = 5.minutes
)

val router = new PolicyBasedReBatchRouter[Item](policy)
// router.route(failures, context)
// → RoutingDecision(item, nextStep, reason)
//   where nextStep ∈ { RetrySameArea, RouteToArea, Manual, Scrap }

// Recharge: BALANCE_INSUFFICIENT→Scrap, TIMEOUT→Retry
// Purchase: QUOTA_EXCEEDED→Scrap, TIMEOUT→Retry
// Difference = one line in ReBatchPolicy.actionMap

8. Resilience Blueprint: From Event Sourcing to Six Nines

M2.5+ is not just about business parameterization — it inherits all of M2's Akka infrastructure capabilities. The ChainExecutionActor reconnects the runtime pipeline to Akka Persistence, ensuring Event Sourcing, Self-Healing, Horizontal Scaling, and Responsive system properties are preserved. Below, we inspect the stability guarantees layer by layer — from application code through hardware.

8.1 ChainExecutionActor: The Event Sourcing Layer for Runtime Pipelines

ChainExecutionActor (new, 342 lines) wraps SubBatchProcessor's Future pipeline in a lightweight EventSourcedBehavior. When each pipeline stage completes, the onPhaseComplete callback sends a PhaseCompleted message back to the actor, triggering event persistence.

Started → PhaseDone(file-gen) → PhaseDone(upload) → PhaseDone(wait-ack) → PhaseDone(poll) → PhaseDone(parse) → PhaseDone(classify) → AllCompleted
Key difference from M2: M2 has ~40 business-specific event types (one per FSM transition). M2.5+ has only 4 generic event types (Started / PhaseDone / AllCompleted / ExecutionFailed). No information is lost — M2's "RechargeRequestFileGenerated" is equivalent to M2.5+' PhaseDone("file-gen", metadata={...}) where metadata carries path, size, and encoding. Recharge/Purchase/Equipment-Area all share the same event types — business variation lives in configuration alone.

8.2 Self-Healing Walkthrough: Full Cluster Outage Recovery

The worst-case scenario — the entire Akka Cluster (all 3 nodes) loses power — and how it recovers, step by step.

// === Before crash, persisted in Journal === Started("recharge", "batch-001", itemCount=500) PhaseDone("file-gen", t=1000, {localPath:"/tmp/batch-001.xml", byteSize:"4096"}) PhaseDone("upload", t=2000, {remotePath:"/remote/batch-001.xml", bytesTransferred:"4096"}) PhaseDone("wait-ack", t=3000, {ackResult:"AckReceived"}) ← Entire cluster goes down (poll was waiting for SFTP response file) // === Recovery === t=0s Akka Cluster reforms (gossip convergence, 3 nodes discover each other) t=2s ShardCoordinator leader elected; assigns shard-7 → node-3 t=3s ChainExecutionActor starts; MongoDB journal replays 4 events state = Executing("batch-001", phases=["file-gen","upload","wait-ack"]) t=4s RecoveryCompleted → itemLoader("batch-001") reloads 500 items from MySQL t=5s processor.process(batch) re-executes full pipeline: file-gen: overwrites temp file (idempotent) upload: overwrites SFTP upload (same MD5, idempotent) wait-ack: re-notifies EAMS (EAMS dedup — returns success for already-seen batch) poll: re-polls SFTP (response file already generated by EAMS, available immediately) parse: re-parses XML response (idempotent) classify: re-classifies results (idempotent) t=8s SMS/P2B notify phase: checks MySQL read-side → batch-001 has no notify record yet → sends SMS + P2B notification t=9s persist AllCompleted("batch-001", success=498, failure=2) → Actor stops. Recovery complete.

Recovery time: ~9 seconds (excluding MongoDB cluster startup). If the cluster crashes again mid-recovery, the process is fully replayable — AllCompleted hasn't been persisted yet, so RecoveryCompleted will trigger again and everything executes idempotently from the start.

8.5 Six Nines Stability Blueprint (99.9999%)

Six dimensions of stability — from application code to hardware networking. Target: annual downtime ≤ 31.5 seconds.

App
Application · Akka
  • Circuit Breaker: external calls protected · SftpConnector / HttpConnector
  • Retry with Backoff: ReBatchPolicy exponential backoff (maxRetries=3)
  • Bulkhead: per-chain shard entity, resource isolation
  • Timeout: SLA config (10min/15min per chain)
  • Dead Letter: failure events persisted to MongoDB journal, fully traceable
JVM
Runtime · JVM
  • GC: G1GC, -Xms4g -Xmx8g, MaxGCPauseMillis=200
  • Thread Pool: Akka Dispatcher fork-join-pool, parallelism-min=8, max=64
  • Memory: -XX:+HeapDumpOnOutOfMemoryError, MaxMetaspaceSize=512m
  • JIT: Tiered Compilation, ReservedCodeCacheSize=256m
  • JMX: MBean exposes actor metrics + GC metrics
Infra
Infrastructure · Cluster
  • Cluster: min 3 nodes (tolerates 1 failure), recommend 5 (tolerates 2)
  • Sharding: ShardCoordinator singleton (auto failover)
  • Persistence: MongoDB 3-node replica set, writeConcern=majority
  • Split Brain: keep-majority strategy (minority self-downs)
  • Membership: akka.cluster.downing-provider-class = SBR
HW
Hardware / Network
  • Multi-AZ: 3 availability zones (≥ 1 node per AZ)
  • Compute: 8-16 vCPU, 16-32GB RAM per node
  • Network: 10GbE · jumbo frames (MTU 9000) · low latency
  • Load Balancer: HAProxy/Nginx TCP mode · health check /health
  • DNS: multi-IP round-robin (TTL=60s) · auto failover
Storage
Storage Layer
  • MongoDB (write): 3-node replica set · journal w: "majority"
  • MySQL (read): primary-replica replication · read replica for queries + dedup
  • Backup: MongoDB daily snapshot + oplog incremental (RPO < 1h)
  • Retention: event journal 30 days · snapshot every 100 events
  • Disk: SSD · 30% headroom reserved
Ops
Operations
  • Health Check: /health endpoint (Akka Management) · readiness + liveness
  • Metrics: Prometheus scrape akka-actor-metrics + jvm-metrics · Grafana dashboard
  • Alerting: PagerDuty (SLA breach / shard imbalance / GC pause > 500ms)
  • Graceful Shutdown: CoordinatedShutdown (Akka Management) · drain → stop → leave
  • Logging: SLF4J + Logback · JSON format · centralized ELK
