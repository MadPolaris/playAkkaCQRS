1.58 Million Rows.
One Database Transaction.
One Lot Start.

Siemens Opcenter EX CR's High Performance Engine technical reference (July 2021) documents a Multi-Level Start transaction that writes 1,580,003 database records in a single Oracle transaction — executed through a chain of stored procedures (clfExecute, clffunc*). Most of those records are audit trail, history tables, and cross-reference inserts — data that belongs to downstream process steps, not the current operation. But because the database transaction is the only consistency guarantee, everything is crammed into one atomic write.

Now project this to 2nm. GAA nanosheet transistors. 2,000–3,000+ process steps per wafer (vs. ~1,000 at 7nm). Multi-patterning at every critical layer. In-line metrology at every step. That 1.58 million rows per Lot is not the ceiling — it's the starting point. At 2nm, we're looking at 5 to 15 million rows per Lot transaction. Oracle and DB2 can execute it — but can they do it while keeping the tool waiting under a second? Can they recover from a mid-transaction failure in under a minute?

What if there's a better way? An open-source reactive MES kernel targeting six nines of reliability. Event sourcing instead of giant transactions. Sagas instead of stored procedures. A streaming DAG execution engine that orchestrates across systems.

The Database-Centric Dead End

This is not a straw man. It's a real case from Siemens/HPE in semiconductor manufacturing.

1,580,003

database records, in a single Oracle transaction. For one Multi-Level Lot Start.

The mechanism? JSON payloads sent to stored procedures (clfExecute, clffunc*) that parse and execute SQL in bulk on the database server — what Siemens calls the "High Performance Engine" (HPE), a separately licensed feature of Opcenter EX CR. No unit tests. No version control for the stored procedure logic. No horizontal scaling.

The kicker: The vast majority of those 1.58 million records aren't needed for the current operation. They're history tables (HistoryMainline, StartHistoryDetail, HistoryCrossRef), current status snapshots, cross-reference indexes, step-pass counters — data that exists to serve downstream queries and audit requirements. But because the database transaction is the only consistency guarantee, everything is chained into one atomic write. The downstream's data pressure gets dragged upstream, and the Lot Start slows to the speed of the largest insert.

Source: Siemens Opcenter EX CR — Technical Reference: High Performance Engine, Release 8G.1 (July 2021).

🔮 Project to 2nm GAA

The 1.58M-row reference is from the 7nm/5nm era (~1,000 process steps per wafer). At 2nm — with GAA nanosheet transistors, high-NA EUV, and 2,000–3,000+ process steps — the number of containers, history records, and cross-references per Lot explodes. Conservative estimate: 5–15 million rows per Lot transaction.

Can Oracle or DB2 execute a 15-million-row stored procedure? Technically yes. But while holding locks across dozens of tables? While the tool sits idle? Can it recover from a mid-transaction failure — not in hours, but in seconds? At 2nm, the stored-procedure approach doesn't just hurt performance — it becomes the bottleneck that caps throughput for the entire Fab.

Tool Waiting = Capacity Loss

Giant transactions hold locks while tools sit idle. In a Fab, every minute of idle tool time is lost revenue that can never be recovered.

Cross-System State Drift

MES says the wafer is at Step 47. EAP says Step 46. RMS has no record. These inconsistencies cause wrong dispatching and wrong recipes — silently.

Brittle Recovery

When a stored procedure spanning 1.58M rows (or 10M+ at 2nm) fails mid-execution, recovery is manual. Hours of downtime while operators and DBAs figure out partial state. No automatic compensation, no partial progress preserved.

Throughput Ceiling at 2nm

A Fab producing 100K wafers/month at 3,000 steps each generates an event storm that dwarfs current MES loads. The stored-procedure-in-a-single-transaction approach doesn't scale — each Lot Start becomes a serialization point.

A Different Path

The root cause isn't "the database is too slow." It's that the consistency boundary is drawn in the wrong place. Audit trail records, history snapshots, cross-reference indexes — they don't belong in the same transaction as the current operation. Cross-system alignment shouldn't rely on foreign keys — it should be event-driven, eventually consistent. Process orchestration shouldn't be hard-coded in JSON-driven stored procedures — it should be explicit, testable, and evolvable DAGs.

This matters now. At 2nm, it becomes existential for Fab throughput.

The Reactive Foundation

The four pillars of the Reactive Manifesto are not abstract principles — they map directly to what a Fab control system demands. Built on Akka (the reference implementation of the Reactive Manifesto, created by its original author Jonas Bonér).

📨

Message-Driven

Asynchronous message-passing is the backbone. Loose coupling and location transparency enable independent scaling of each subsystem — EAP signals, MES state changes, SPC alerts all flow as messages.

Fab: Tool signals arrive as messages, never block the sender
🛡️

Resilient

Failures are contained within individual components. Supervision hierarchies isolate faults so a single tool integration failure doesn't cascade across the entire Fab control system.

Fab: One EAP connection failure doesn't take down MES
📈

Elastic

Scale up and down with load. Cluster Sharding distributes entity instances across nodes — when a new Fab line comes online, the system absorbs it without rewiring.

Fab: Add a new production line without re-architecting
⚡

Responsive

Rapid, consistent response times under all conditions. Non-blocking I/O and back-pressure ensure predictable latency — the instant feedback loop that Fab operations depend on.

Fab: Tool dispatch responds in milliseconds, not seconds

Event Sourcing × CQRS

Event Sourcing and CQRS are the two patterns that make the reactive MES kernel work. They solve problems that database-centric architectures can't.

Event Sourcing

State is derived by replaying an immutable event journal. Every state change — tool assignment, wafer move, recipe execution — is captured as a domain event. Complete audit trail, temporal queries (what was the state at 14:03:27?), and reliable debugging. Akka Persistence handles journaling and snapshots.

CQRS — Separate Reads from Writes

Commands mutate state on the write side (event-sourced aggregates). Queries read from optimized projections (MySQL). The write side stays fast because it only appends events. The read side is free to denormalize, index, and optimize for every query pattern independently.

Real-Time Projections

Akka Projections transform the event stream into read-model tables. Each projection subscribes to tagged events from a specific aggregate type, processes them transactionally, and updates MySQL — providing eventually-consistent views with at-least-once delivery guarantees.

Saga Pattern (TCC)

Distributed transactions without distributed locks. Try-Confirm/Cancel: each step reserves resources (Prepare), then either commits or compensates. Failures trigger backward recovery — only steps that succeeded in Prepare get compensated. Suspended transactions support manual intervention.
