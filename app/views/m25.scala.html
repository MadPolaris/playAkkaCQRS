二、M2.5+ 解法：三层分离架构

M2.5+ 将系统划分为三个正交维度——业务维度定义步骤序列与批次管理、 技术维度封装通信协议栈与容错组件、业务调度维度标准化结果分流与异常处理。 每个维度独立演进、独立测试、独立修复，组合起来覆盖完整的跨系统编排生命周期。

工单 → 批次管理器拆批 → 单批次工序序列管理器推进步骤 → 业务步骤链执行 → 技术组件支撑远程通信 → 批量结果散射器三路分流 → 异常调度 / 再确认

三层维度组件

业务维度 · 步骤管理与执行

📋
批次管理

批次管理器

将工单拆分为多个批次生产，管理批次生命周期。每个批次包含 ×2000 制造单元，独立推进业务步骤序列。

🔀
步骤推进

单批次工序序列管理器

管理当前批次所在的业务步骤，推进/回退步骤序列。5 个标准步骤模板：① 额度资源锁定 → ② 批量充值 → ③ 批量申购 → ④ 结果批量通知 → ⑤ 额度资源解锁。每步骤 4 个标准工序：请求发起 → 收集结果 → 结果散射 → 结果再确认（全部异步、事件驱动）。

技术维度 · 标准化可复用组件

📦
物理约束

出站缓冲 · 重新成批

按物理约束（FOUP 容量、时间窗口、同 recipe 混批策略）重新成批后分派到设备。薪资场景约束宽松（1–100 笔），Fab 场景约束严格（FOUP 25 片）。

⚡
容错

断路器

内建重试 · 超时 · 熔断 · 恢复机制。所有外部通信统一经过断路器保护，故障隔离不扩散。

🔄
格式

编解码

JSON / XML / CSV / 加密文件格式转换，编码策略与连接器解耦。新增报文格式只需实现 Codec 接口。

🔒
安全

安全加密

传输层 TLS / 应用层 AES / 国密 SM4。加密策略参数化，按外部系统安全等级自动选择。

🔌
通信

通信协议栈

SFTP / HTTP-XML / HTTP-JSON 多协议适配。新增传输协议只需实现 Connector 接口，不影响上层业务逻辑。

业务调度维度 · 结果分流与异常处理

🎯
分流

批量结果散射器

对每个制造单元的远程通信结果进行三路分流：✅ 成功 → 继续下一个业务步骤；❌ 失败 → 上报异常调度器；⚠️ 可疑 → 发送再确认组件。全部异步事件驱动。

🚨
异常

异常调度器

接收散射器上报的失败结果，经过缓冲（空间约束）与超时（事件约束）后发出向前补偿请求到批次管理器，重新指定业务步骤（补偿/跳过/终止）。

🔍
复核

再确认组件

对可疑结果进行二次查证（通过更高精度量测、Core API 核验或人工复核），确定最终成功/失败后回传散射器。不是流水线的必经阶段——成功和失败项不经过这里。

关键设计决策：三层分离 vs 单体 FSM。 业务维度定义"做什么"（步骤序列），技术维度提供"怎么做"（通信/容错/加密），调度维度决定"结果去哪"（成功推进/失败补偿/可疑复核）。 三层分离意味着：业务人员修改步骤序列不需碰技术组件；基础设施团队升级断路器不需理解业务逻辑；调度策略变更（如"可疑阈值从 5% 调至 3%"）是参数配置而非代码修改。 区别于 M2 的手写 FSM：组件在运行期按参数实例化——修 bug 改一次组件，所有实例自动继承修复。

三、业务参数化：三个维度，各自配置

M2.5+ 的核心价值不在于"消除了多少行代码"，而在于修改的爆炸半径。 三个维度的参数各自独立：业务维度配置步骤序列与批次约束，技术维度配置协议/重试/加密策略，调度维度配置分流规则与补偿策略。 产品经理关心的参数从代码深处提升到配置层，每个维度独立变更、独立验证。

7.6 具体消息例子：M2 业务消息的 M2.5+ 等价形式

以下 3 组对比展示 M2 中一个完整业务流程的多个消息/事件如何在 M2.5+ 中被等量信息地承载。

例 1：发起充值请求——M2 FSM 到 M2.5+ Pipeline 的等价映射

M2 的 StartRechargeRequest → FileGenerating → FileGeneratedCompleted → FileUploading → RequestUploadFile → ... 是一次完整的 FSM 状态迁移链条。M2.5+ 用 Pipeline 的 Future 链替代。

M2 Java — RechargeRequestActor（300+ 行 FSM）
// 300+ 行 FSM: query DB → generate CSV → compute MD5 → update status
case New:
  on StartRechargeRequest:
    List<SalarySavingItem> plans = db.queryValidItems(batchId);
    generateRechargeFile(plans);          // 写 .txt + .md5
    updateBatchStatus(FileGenerating);
    tell self FileGeneratedCompleted;     // 触发下一状态
    → state = FileGenerating

// FileGenerating → FileUploading:
case FileGenerating:
  on FileGeneratedCompleted:
    updateBatchStatus(FileGenerated);
    tell self RequestUploadFile;
    → state = FileUploading

// FileUploading → FileUploaded:
  tells SftpService SftpCommand.UploadFile(path, remotePath)
  on SftpCommand.FileUploadComplete:
    updateRemoteFilePath(remotePath);
    → state = FileUploaded

// ↑ 每个状态迁移 = 命令 → 事件 → 副作用 → 新状态
M2.5+ Scala — SubBatchProcessor（流水线内部无 FSM）
// SubBatchProcessor 内部用 Future 链直接执行：
val processor = new SubBatchProcessor[Item, Raw](pipeline)

// 6 阶段 Future 链：
def process(batch: SubBatch[Item]) =
  for {
    file  <- pipeline.fileGen.generate(items, ctx)
    // ↑ 等价于: StartRechargeRequest → FileGenerating → FileGeneratedCompleted
    rcpt  <- pipeline.upload.upload(file, ctx)
    // ↑ 等价于: RequestUploadFile → SftpCommand.UploadFile → FileUploadComplete
    ack   <- pipeline.waitAck.waitForAck(rcpt, ctx)
    // ↑ 等价于: RequestNotifyEams → EamsNotifyCreated
    resp  <- pipeline.pollResp.poll(ctx)
    raw   <- pipeline.parse.parse(resp, ctx)
    cls   <- pipeline.classify.classify(raw, batch.items)
  } yield SubBatchResult(cls)

// 流水线内部无显式状态——阶段间通过类型变化连接
// 事件溯源和状态恢复由外层 ChainExecutionActor 提供（详见第 8 章）

例 2：结果分类——从硬编码 if-else 到配置驱动的三分类器

M2 的 RechargeResponseActor.rechargeResponseFile() 方法中 AwaitResultRequested(items) 包含分类结果。M2.5+ 用 ErrorCodeMapping 配置驱动。

M2 Java — RechargeResponseActor
// RechargeResponseActor.rechargeResponseFile():
for (RechargeResponseItem item : items) {
  if (item.result == 1)
    successItems.add(item);           // → RechargeSuccessActor
  else if (item.result == 2)
    failureItems.add(item);           // → RechargeFailureActor
  else if (item.result == 99)
    pendingItems.add(item);           // → RechargeReconfirmActor
  else
    failureItems.add(item);           // 未知=失败
}

// 申购的 PurchaseResponseActor 同样的逻辑：
// if (status == 0) success; else if (status == 1) failed; else pending;
// ——只是状态码不同，但需要单独一个 Actor 文件
M2.5+ Scala — ErrorCodeBasedClassifier
// 纯配置驱动——无需修改分类器代码
// 只改 ErrorCodeMapping 即可切换业务

七、运行保障全景：从事件溯源到 6 个 9 稳定性

M2.5+ 不只是业务参数化的抽象——它继承了 M2 的全部 Akka 基础设施能力。 ChainExecutionActor 将运行时流水线重新接入 Akka Persistence，确保事件溯源、自愈恢复、水平扩展、响应式四大架构目标完整保留。 以下从软件层到硬件层，逐层展示系统的稳定性保障。

8.1 ChainExecutionActor：运行时流水线的事件溯源层

ChainExecutionActor（新增 342 行）用一个轻量 EventSourcedBehavior 包装了 SubBatchProcessor 的 Future 流水线。每个流水线阶段完成时，通过 onPhaseComplete 回调向 Actor 自身发送 PhaseCompleted 消息，触发事件持久化。

Started → PhaseDone(file-gen) → PhaseDone(upload) → PhaseDone(wait-ack) → PhaseDone(poll) → PhaseDone(parse) → PhaseDone(classify) → AllCompleted
与 M2 的关键区别：M2 有 ~40 个业务专用事件类型（每个 FSM 状态迁移一个）， M2.5+ 只有 4 个通用事件类型（Started / PhaseDone / AllCompleted / ExecutionFailed）。 信息量没有丢失——M2 的 "RechargeRequestFileGenerated" 等价于 M2.5+ 的 PhaseDone("file-gen", metadata={...})，metadata 承载了文件路径、大小等细节。 充值/申购/设备区复用同一套事件类型，业务差异完全在配置中。

8.2 自愈推演：集群全部宕机后如何恢复

以下展示最坏场景——整个 Akka Cluster 全部宕机（所有 3 个节点断电），然后逐步恢复。

// === 宕机前，Journal 中已持久化 === Started("recharge", "batch-001", itemCount=500) PhaseDone("file-gen", t=1000, {localPath:"/tmp/batch-001.xml", byteSize:"4096"}) PhaseDone("upload", t=2000, {remotePath:"/remote/batch-001.xml", bytesTransferred:"4096"}) PhaseDone("wait-ack", t=3000, {ackResult:"AckReceived"}) ← 集群全部宕机（poll 正在等待 SFTP 响应文件） // === 恢复过程 === t=0s Akka Cluster 重新形成（gossip convergence，3 节点互相发现） t=2s ShardCoordinator 选主完成，分配 shard-7 → node-3 t=3s ChainExecutionActor 启动，MongoDB journal 回放 4 个事件 state = Executing("batch-001", phases=["file-gen","upload","wait-ack"]) t=4s RecoveryCompleted → itemLoader("batch-001") 从 MySQL 重新加载 500 条 items t=5s processor.process(batch) 重新执行完整流水线： file-gen: 覆盖 temp file（幂等） upload: 覆盖 SFTP upload（相同 MD5，幂等） wait-ack: 重新通知 EAMS（EAMS 去重——已处理过的 batch 返回 success） poll: 重新轮询 SFTP（响应文件已由 EAMS 生成，立即可下载） parse: 重新解析 XML 响应（幂等） classify: 重新分类结果（幂等） t=8s SMS/P2B notify 阶段：检查 MySQL read-side → batch-001 尚无 notify 记录 → 发送 SMS + P2B 通知 t=9s persist AllCompleted("batch-001", success=498, failure=2) → Actor stop。恢复完成。

恢复耗时：~9 秒（不含 MongoDB cluster 启动时间）。如果中途再次宕机，流程完全可重放—— AllCompleted 尚未持久化，RecoveryCompleted 将再次触发恢复，一切从头幂等执行。

App
应用层 · Akka
