1. Why a DAG Execution Engine

M1 Saga solved the atomicity problem of a single distributed transaction. But real business scenarios involve long-chain orchestration across multiple external systems — cron triggers, file generation, SFTP uploads, response polling, classification, exception routing, downstream notifications — this is not something a simple request-response can cover. M2 DAG Execution Engine models cross-system workflows as Directed Acyclic Graphs (DAGs), where each node is an independent Persistent FSM and edges represent data flow and dependencies.

2. 5-Level DAG Architecture

M2 decomposes cross-system orchestration into 5 vertical levels, each with clear responsibility boundaries. Data flow between levels is unidirectional — upper levels pass instructions down, lower levels feed results up. Exceptions flow back to upper levels via compensation loops.

L0 Trigger → L1 Orchestration → L2 Execution & Resources → L3 Business Chain → L4 Communication → L5 Compensation & Release

3. Four Resilience Patterns

M2's 23 FSMs have 4 built-in resilience patterns. These aren't afterthought try-catch blocks — each FSM's type is itself a resilience strategy.

🎯

Orchestrator

Handles job splitting, batch management, and phase advancement. After each phase completes, continuously checks preconditions for the next phase. If a child node fails, the Orchestrator decides whether to retry or initiate the compensation chain. Actors: JobActor, PreBatchActor, BatchMaster.

🛡️

Protector

Declares system invariants, enforced by the engine. Example: "Lock auto-releases after 30 seconds" — even if the node crashes, the timer triggers release after recovery. A Protector is not a try-finally — it's a persistent guardian of invariants. Actors: UserQuotaReservation, QuotaRelease.

📡

Communicator

Encapsulates all interactions with external systems. Models SFTP uploads, HTTP requests, and response polling uniformly as asynchronous messages. External uncertainty is isolated within retryable boundaries. Circuit breakers protect downstream systems. Actors: All 12 L3 business chain FSMs + all L4 gateways.

↩️

Compensator

The final safety net. As long as the Compensator is running, no failure is missed. ReBatchActor ensures eventual success through infinite retry — automatically requeues after each failure. The compensation and release layer guarantees that all locked resources are eventually freed.

Why 4 patterns are enough: Every participant in cross-system orchestration can be classified into one of these 4 roles. Orchestrator "advances," Protector "guards," Communicator "talks," Compensator "catches." The combination of these 4 patterns covers the complete loop from scheduled trigger to final resource release.

4. Stream-Batch Unified Pipeline

In traditional architectures, streaming (real-time messages) and batch (file transfers) require two separate processing systems — different triggers, different execution paths, different error handling. M2 unifies both through a single DAG pipeline.

📂

Batch Path

Cron trigger → generate files → SFTP upload → poll response files → parse + classify → create sub-batches → concurrent processing → aggregate results. Used for payday batch deposits and reconciliation file processing.

⚡

Streaming Path

Skip file generation and SFTP — receive events directly from message queue/HTTP → parse + classify → create sub-batches → concurrent processing → aggregate results. Used for real-time transactions and instant notifications.

Shared core: Whether batch or streaming entry, the execution pipeline from L2 downward is completely identical — BatchWorker's concurrent processing, the business chain's request-response-reconfirm-notify pattern, the compensation release layer's resource reclamation — all reused, zero duplicated code.

5. From M2 to M2.5+: From Hand-Written FSMs to Standard Components

M2 proved the feasibility of the "cross-system DAG orchestration engine" — 23 Persistent FSMs successfully completed the salary deposit scenario. But it also revealed a core limitation: each business scenario requires writing 23 FSMs from scratch. From salary deposit to Fab equipment communication, although the flow structure is highly similar (file gen → upload → poll → parse → classify → route), every scenario required rewriting all FSMs. M2.5+ abstracts these patterns into 6 standard components — fix once, apply everywhere.
