1. Why Saga

In microservices and CQRS/ES architectures, data is distributed across multiple aggregates and external systems. Traditional 2PC (Two-Phase Commit) relies on database locks and a transaction manager, creating fatal flaws in distributed scenarios: long lock durations, single points of failure, incompatibility with heterogeneous data sources. Saga splits a global transaction into a series of local transactions, with each step independently executed and compensated — achieving lock-free distributed consistency.

Dimension2PC / Stored ProceduresSaga (M1)

Lock ScopeAll involved rows locked for entire durationEach step locks local resources only during its execution
Failure RecoveryDatabase auto-rollback entire transactionSaga auto-compensates succeeded steps; compensation failure → SUSPENDED manual intervention
Heterogeneous SourcesMust be the same database instanceEach step can target different databases, APIs, message queues
ObservabilityInternal transaction state invisibleEvery step persisted as an event — complete audit trail
Horizontal ScalingLimited by single-DB transaction throughputAkka Cluster Sharding by transaction ID — horizontal scale-out
Key insight: In a Fab Lot Start scenario, the vast majority of 1.58M rows are downstream data (history snapshots, audit trails, cross-references). Saga doesn't wait for "everything to be written" before committing — the current operation completes first, and downstream data is written asynchronously via events. The consistency boundary shrinks from "the entire operation" to "the current step" — this is the root of the throughput improvement.

2. Architecture: Three-Layer Orchestration Model

M1 Saga uses the Orchestrator-Driven pattern. The Saga is not an abstract concept — it's an independent infrastructure layer (saga-core). The business layer only needs to implement Participant interfaces.

Application Layer (Facade + Participant) → Orchestration Engine (Coordinator + StepExecutor) → Infrastructure (Persistence + Sharding)

Module independence: The Saga orchestration engine is a standalone library (saga-core/) with zero business dependencies. The application layer (app/) binds Participant implementations via dependency injection. This means a single Saga engine can drive any distributed transaction scenario — money transfer, Fab Lot Start, cross-system data alignment — just by providing different Participant implementations.

3. TCC Three-Phase Model

M1 Saga uses the Try-Confirm/Cancel (TCC) pattern. Each step doesn't directly execute an operation but goes through three phases. Steps can be grouped for parallel execution (same group = concurrent).

🔒

Prepare (Reserve)

Check preconditions, reserve resources, but do not commit. E.g., verify sufficient balance, lock a FOUP slot. If any Prepare fails → trigger backward compensation for all succeed-Prepare steps. The Prepare phase represents reversible operations.

✅

Commit (Confirm)

Confirm execution, data is truly persisted. E.g., actual debit, write status table. After all Prepare steps succeed, the Commit phase begins. Commit failure also triggers compensation — only Commit-succeeded steps need compensation. Commit represents irreversible but compensatable operations.

↩️

Compensate (Cancel)

Undo the business impact of completed steps — not a database ROLLBACK. E.g., refund money, release locked slots. Compensation itself can fail — in that case Saga doesn't deadlock but enters SUSPENDED state, awaiting manual intervention: ManualFixStep + RetryCurrentPhase.

Group parallelism: Steps in the same group (stepGroup) execute concurrently; different groups are serial. Once all steps in a group succeed in Prepare, they proceed to Commit together. This guarantees intra-group parallelism, inter-group sequencing.

SUSPENDED is not deadlock: When compensation fails (e.g., refund API unreachable), Saga enters SUSPENDED state, but all intermediate state is already persisted in Akka Persistence. Operators use the emergency fix panel to view suspended transactions, sending ManualFixStep(stepId, phase) → RetryCurrentPhase to resume execution. No state is ever lost.

5. Backward Recovery Mechanism

When a step fails during Prepare or Commit, Saga doesn't push forward — it performs backward compensation — only compensating steps that already succeeded in the current phase. This approach guarantees:

🎯

Precise Compensation Scope

The Coordinator maintains a successfulSteps set — tracking only steps that succeeded in the current phase (Prepare/Commit/Compensate). Compensation targets only this set — no double-compensation, no missed steps.

⚡

Concurrent Execution & Stop

Upon detecting a failure, the Coordinator first stops all unfinished child StepExecutors, then initiates Compensate for each step in successfulSteps. Compensation can execute in parallel.

🔄

Idempotent Recovery

When a StepExecutor in Succeed state receives a Start command, it directly returns the cached execution result without re-executing — preventing double-deduction, double-shipment, etc. This guarantee holds across node restarts.

Core logic of Backward Recovery: Compensate only succeeded steps. If compensation fails, suspend (SUSPENDED) until human confirmation or system recovery. This differs from database ROLLBACK — Saga's compensation is a new business operation that itself can fail, requiring the SUSPENDED mechanism as a safety net.

Protobuf Triple Rule: When modifying any Saga-related data structure, you must synchronize (1) Scala Case Class, (2) .proto file, (3) Proto Converter (toProto/fromProto). Inconsistency between the three causes serialization failures.
