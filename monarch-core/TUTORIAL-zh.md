# 白话教程：一次基金申购批的奇幻漂流

本文不讲术语，先讲一个你天天在见的业务故事。读完再回头看[参考手册](README-zh.md)，那些"游标、世代号、拦截器"就都对上号了。

**场景**：某银行理财渠道，每天定时把积攒的基金申购单**打包成批**，送给基金公司处理，然后取回结果，逐笔告诉客户成功还是失败。

今天这批有 **5 笔申购**，批次号 `batch-20240601-001`。

---

## 第 1 幕：走完整个流程（没出事的情况）

这批单子要过六道工序，一道都不能少、顺序不能乱：

| 工序 | 业务动作 | 做完之后，手头多出来的东西 |
|---|---|---|
| ① 生成文件 | 把 5 笔申购单写成基金公司要求的对账文件 | `/tmp/batch-20240601-001.xml` |
| ② 上传 | 把文件传到基金公司的 SFTP 目录 | 上传回执（远端路径、字节数、时间） |
| ③ 等回执 | 等基金公司确认"收到文件了" | 回执：收到 ✓ |
| ④ 轮询结果 | 定时去基金公司目录拉取处理结果文件 | 结果文件 `response-001.xml` |
| ⑤ 解析 | 把结果文件拆成逐笔状态 | 5 行：`申购1=成功，申购2=成功，申购3=成功，申购4=成功，申购5=成功` |
| ⑥ 逐笔分类 | 按错误码把每笔归入 成功/失败/可疑 | 客户通知名单 |

六道工序走完，引擎把结果吐给你：**5 笔全部成功**，今天的活干完了。

> 这六道工序，在 Monarch 里叫 **六个阶段（Stage）**；
> 那份"手头多出来的东西"不断增多的记录，叫 **状态（State）**；
> 引擎每走完一道就喊一嗓子"我做完了第 N 道"，让你的程序记账，这个记账动作叫 **journal**。

---

## 第 2 幕：干到一半，机房断电了

真实世界没那么顺利。这次跑到**第 ③ 道等回执**的时候，机房断电，程序挂了。

问题来了：重启之后，这批申购单怎么办？

- ①② 已经做完（文件生成了、也传出去了）——**绝对不能重做**，不然基金公司会收到两份一样的文件；
- ③ 还没等到回执——**必须从③继续等**；
- ④⑤⑥ 还没做。

如果你手头有一本**流水账**，这就不是问题。Monarch 的宿主（这里是 `ChainExecutionActor`）每做完一道工序，就在账本上记一行：

```
第 1 笔账：file-gen  完成，产物 = /tmp/batch-001.xml
第 2 笔账：upload    完成，产物 = 上传回执
第 3 笔账：wait-ack  完成，产物 = 收到 ✓
（断电 ⚡）
```

关键在于：**每笔账不只记"做完了"，还把做完之后手头的东西（产物）复印一份订在账本后面**。程序重启后：

1. 先把账本从头读一遍——知道做完了 3 道；
2. 把第 3 笔账后面订着的产物复印件取出来——手头立刻恢复到断电前的样子；
3. **从第 ④ 道"轮询结果"接着干**。①②③ 一道都不重做。

这就是文档里说的 **断点续跑**。术语对照：

| 白话 | 文档术语 | 代码符号 |
|---|---|---|
| 账本上"做到第几道了" | 游标（cursor） | `resumeFromIndex(state, 已完成道数)` |
| 订在账本后面的产物复印件 | 快照（snapshot） | `PhaseDone(..., snapshot = 状态)` |
| 每道工序 | 阶段（stage） | `BankStage.FileGen / Upload / ...` |
| 手头不断增多的东西 | 状态（state） | `BankChainState` |

## 第 3 幕：5 笔里有人失败、有人失联

这次流程走完了，但第 ⑤ 道解析出来的结果不齐：

| 申购单 | 基金公司返回 | 归类 |
|---|---|---|
| 申购 1、2、3 | 认购成功 | ✅ 成功——通知客户 |
| 申购 4 | **余额不足** | ❌ 失败——这笔钱注定扣不到，不用再试 |
| 申购 5 | **处理中超时** | ❓ 可疑——到底成没成？不知道，得查 |

第 ⑥ 道分类会把它们分成三堆。接下来是两套**业务策略**（注意：这些都是你的业务代码在管，不是引擎管的）：

**可疑 → 查证落定**：申购 5 的"超时"不能悬着。调基金公司的查询接口查证：真没成功 → 归入失败；其实成功了 → 归入成功。查完还不确定？保守按失败处理，进人工复核。这就是"可疑复核"（代码里的 `ReconfirmHandler`）。

**失败 → 重批**：申购 4 余额不足直接失败；但如果失败原因是"网络超时"呢？按你配的策略——等 5 分钟，**重新打包送一次**。这个"失败项重新组批再走一遍"就是 **ReBatch**。策略长这样：

```scala
onFailure { r =>
  r.maxRetries(3)                                   // 最多重试 3 次
  r.when("NETWORK_ERROR") { RetrySameArea(30.seconds) }  // 网络错：30 秒后重试
  r.when("BALANCE_INSUFFICIENT") { Scrap }          // 余额不足：放弃
  r.otherwise { ManualIntervention("人工工单") }      // 其他：转人工
}
```

重试 3 次还失败？升级成人工工单，绝不无限重试。

## 第 4 幕：升级重启时，"上一个我"还在跑

最阴险的场景：程序正在处理批次，你发布了新版本，老进程被杀、新进程起来。但**老进程里有一条没跑完的处理链还挂在内存里**（Java 线程不会因为你"逻辑上"重启了就消失）。

如果不设防，就会出现两个"我"同时处理同一批申购单——给基金公司传两份文件、给客户发两条短信。

Monarch 的解法简单粗暴：**给每一次启动编号（第 1 代、第 2 代……）**。新的一代注册时，旧一代自动作废；旧链跑到下一道工序的门口一查"我是第 1 代？现在已经是第 2 代了？"——**自己悄悄退场，一道工序都不再碰**。

这就是"**世代号**"。白话版：新老交接，老的对新的说"活我干到哪了都写在账本上了，你接着来"，然后放下工具走人。

## 5. 三个引擎机制 ↔ 三个业务问题（总对照表）

| 业务问题 | Monarch 的回答 | 机制名 | 源码入口 |
|---|---|---|---|
| 做到一半断了，怎么接着做？ | 每道工序记账 + 产物快照，恢复时跳过做完的 | 断点续跑 | `resumeFromIndex` / `RunRegistry` |
| 阶段失败了怎么办？ | 分两类：业务失败（带错误码）走你的处置策略；意外错误标记 UNEXPECTED | 失败拦截 | `FailureInterceptor` |
| 旧进程的残留任务会不会捣乱？ | 世代编号，旧链在下一道工序门口自动退场 | 世代守卫 | `RunRegistry` / `StaleRun` |

引擎**不管**的事：账本存在哪（MongoDB）、单子怎么跟基金公司传（SFTP）、可疑怎么查证（查证接口）、失败怎么重批（重批队列）——都是宿主的业务代码。引擎只保证一件事：**控制流永远是对的**——顺序不乱、断点准确、失败处理恰好一次、没有僵尸任务。

## 6. 两个真实宿主（同一个引擎）

| | 银行链（充值/申购基金） | Fab 晶圆厂（M3.5 自愈演示） |
|---|---|---|
| 阶段 | 6 道：生成文件→上传→等回执→轮询→解析→分类 | 17 道：装舟→转运→上机→跑 recipe→量测→OCAP 处置→…… |
| 失败处置 | 无拦截器：失败即终止，失败项进重批队列 | OCAP 拦截器：按规则返工/报废/挂起，处理完继续走 |
| 宕机恢复 | 从 PhaseDone 快照断点续跑 | 崩溃在 `Measure#9`，10 秒后从 `#9` 恢复走完全部 |

两边的接入方式一模一样：**写阶段解释器 → 定义游标名 → 把钩子接到日志上 → （可选）配一个失败处置器**。五步建模法见[参考手册 §2](README-zh.md)；完整业务文档见 [ChainDsl 指南](../docs/CHAINDSL_GUIDE-zh.md)。
