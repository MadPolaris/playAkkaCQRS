# 白话教程：一次基金申购批的奇幻漂流

写给做过**银行批处理**的人：充值、申购基金、代付工资——只要是把"一批单子打包送给外部机构、再取回结果逐笔回告"的活，都算。

本文先把你踩过的坑一个一个列出来，再讲每个坑是怎么被填上的。读完你会发现自己不用学任何新概念——**那些坑你本来就懂，只是第一次有人给解法起了名字**。

技术参考手册在[这里](README-zh.md)。

---

## 开篇：批处理老兵的六个噩梦

### 噩梦一：程序挂了，这批单子算处理到哪了？

凌晨两点批量任务跑到一半服务器重启。值班同学被电话叫醒，打开 Excel 开始人肉对账：文件传出去没有？回执等到没有？哪些单子已经通知了客户？

最要命的是两个都不敢做：**整批重跑**——前面已经成功的会重复扣款、重复发短信；**从中间续跑**——谁知道中间是哪？续错了更乱。

最后往往选择"整批重跑 + 人工兜底退重"，一折腾就是一宿。

### 噩梦二：新老版本交接，两边同时发文件？

程序正在跑批量，运维要发新版本。老进程被杀了——但老进程里**有一条没跑完的处理链还挂在内存里**，它不知道自己"已经死了"。新进程起来接着干。结果基金公司收到**两份一模一样的申购文件**，客户收到两条"申购成功"短信。

双跑。运维和开发互相看了一眼，谁都没错，但事故发生了。

### 噩梦三：回执超时的单子，钱到底扣没扣？

结果文件里一笔单子返回"处理超时"。这是成功还是失败？**不知道**——请求发出去了，扣款可能已经发生。不敢自动重试（真成功了就是重复申购），不敢直接报失败（客户明明买了）。最后全部转人工，一个一个调基金公司接口查证。

### 噩梦四：失败重试的策略，为什么改个次数要发版？

失败的代付单要不要重试？业务说"网络问题重试三次，每次间隔五分钟；余额不足直接拒绝；其他情况转人工"。开发把 if-else 写死在代码里。三个月后业务说"网络问题改成重试五次"——**改一行配置的需求，走了两周发版流程**。

### 噩梦五：监管检查要逐笔追溯

监管问：这笔申购单，哪天几点几分生成的文件、什么时候传出去的、回执几点到的、谁批准的重试？如果每一步没有留痕，只能翻应用日志拼时间线——还是碰运气。

### 噩梦六：充值做完做申购，申购做完做代付，每个都从头写？

回头看，充值、申购、代付——**六道工序一模一样**：生成文件、上传、等回执、轮询、解析、逐笔分类。不一样的是什么？错误码（充值看"余额不足"，申购看"额度超限"）和失败策略。但每次新接一个业务，还是把那套流水线代码复制一遍改一遍。

## 这六个坑，Monarch 一个一个填

| 噩梦 | Monarch 的解法 | 你会接触到的名字 |
|---|---|---|
| 一：断电后做到哪了 | 每道工序记账，**账本上还订着做完后的产物**，重启后从断点接着做 | 断点续跑（`resumeFromIndex`，账本上的"游标"） |
| 二：双跑 | 给每次启动编号（第 1 代、第 2 代…），旧一代在下一道工序门口自动退场 | 世代守卫（`RunRegistry`、世代号 `runToken`） |
| 三：超时可疑 | 三分类：成功/失败/**可疑**；可疑必须查证落定，不许悬着 | 三分类（`Classification`）、可疑复核（`ReconfirmHandler`） |
| 四：策略改一次发一次版 | 策略即配置：错误码 → 动作，改配置不改代码 | 重批策略（`ReBatchPolicy`、`NextStep`） |
| 五：逐笔追溯 | 每道工序一条事件：谁、何时、产物是什么，全在账本 | 事件溯源（`PhaseDone` 事件 / journal） |
| 六：每个业务从头写 | 六道工序是共用骨架；换业务只换错误码映射和策略 | 声明式定义（`ChainDsl.define`、`ErrorCodeMapping`） |

下面的故事把六个填坑过程演一遍。每一幕开头标注它在解决哪个噩梦。

---

## 第 1 幕：先看流程本身（噩梦六的铺垫）

5 笔基金申购单，批次号 `batch-20240601-001`，要过六道工序：

| 工序 | 业务动作 | 做完之后手头多出来的东西 |
|---|---|---|
| ① 生成文件 | 5 笔申购单写成基金公司要的对账文件 | `/tmp/batch-20240601-001.xml` |
| ② 上传 | 传到基金公司 SFTP 目录 | 上传回执（远端路径、字节数、时间） |
| ③ 等回执 | 等基金公司确认"收到文件" | 回执：收到 ✓ |
| ④ 轮询结果 | 拉取处理结果文件 | `response-001.xml` |
| ⑤ 解析 | 拆成逐笔状态 | 5 行逐笔结果 |
| ⑥ 逐笔分类 | 按错误码归入 成功/失败/可疑 | 客户通知名单 |

> 这六道工序，Monarch 叫**六个阶段（Stage）**；那份不断增多的"手头的东西"，叫**状态（State）**。
> 注意：工序是骨架，错误码是血肉——换业务换的是血肉（噩梦六），这就是为什么骨架可以只写一次。

---

## 第 2 幕：干到一半断电了（解决噩梦一 + 五）

跑到**第 ③ 道等回执**时机房断电。重启后，宿主程序（`ChainExecutionActor`）把账本从头读一遍：

```
第 1 笔账：file-gen  完成 ✓   产物 = /tmp/batch-001.xml
第 2 笔账：upload    完成 ✓   产物 = 上传回执
第 3 笔账：wait-ack  完成 ✓   产物 = 收到 ✓
（断电 ⚡）
```

两个动作：

1. 数账本——做完了 3 道，**前 3 道一道都不重做**（不然基金公司收到两份文件）；
2. 把第 3 笔账后面**订着的产物复印件**取出来——手头立刻恢复到断电前的样子——从第 ④ 道"轮询结果"接着干。

顺带解决噩梦五：这本账每笔都记着**谁、何时、产物是什么**，监管要逐笔追溯，账本本身就是答案，不用翻日志拼时间线。

> 白话 → 术语：账本上的进度 = **游标**；订着的产物复印件 = **快照**；"从第 4 道接着做" = `resumeFromIndex(状态, 3)`。

## 第 3 幕：有人失败、有人失联（解决噩梦三 + 四）

这次 5 笔结果不齐：

| 申购单 | 基金公司返回 | 归类 |
|---|---|---|
| 申购 1、2、3 | 认购成功 | ✅ 成功——通知客户 |
| 申购 4 | **余额不足** | ❌ 失败——钱注定扣不到 |
| 申购 5 | **处理中超时** | ❓ 可疑——成没成不知道 |

两套业务策略各管一摊：

**可疑 → 查证落定**（噩梦三）：申购 5 不许悬着。调基金公司查证接口：没成 → 归失败；成了 → 归成功；查完还不确定 → 保守按失败、转人工复核。规则只有一条：**可疑是暂时的，落定是必须的**。（代码里的 `ReconfirmHandler`）

**失败 → 按策略重批**（噩梦四）：申购 4 余额不足，重试也是白试，直接拒绝。但如果失败原因是"网络超时"呢？按配置等 5 分钟重新组批再送。策略是配置，不是代码：

```scala
onFailure { r =>
  r.maxRetries(3)                                        // 最多重试 3 次
  r.when("NETWORK_ERROR") { RetrySameArea(30.seconds) }  // 网络错：30 秒后重试
  r.when("BALANCE_INSUFFICIENT") { Scrap }               // 余额不足：放弃
  r.otherwise { ManualIntervention("人工工单") }           // 其他：转人工
}
```

改"重试三次"为"五次"？改配置，不发版。重试 3 次还失败？自动升级人工工单，绝不无限重试。

---

## 第 4 幕：升级重启，"上一个我"还在跑（解决噩梦二）

程序正在跑批量，新版本发布，老进程被杀。但老进程里那条**没跑完的处理链**还挂在内存里——Java 线程不会因为"逻辑上重启了"就消失。

Monarch 的解法：**给每次启动编号**。第 1 代被杀、第 2 代注册的瞬间，第 1 代作废。老链跑到下一道工序门口一查："我是第 1 代？现在已经是第 2 代了？"——**放下工具，悄悄退场，一道工序都不再碰**。

活怎么交接？账本上全写着（第 2 幕），新一代自己读。

> 白话 → 术语：启动编号 = **世代号**（`RunRegistry` 注册）；自动退场 = 下一阶段边界的 `StaleRun`。

## 第 5 幕：下一个业务是"代付"（解决噩梦六）

六道工序一个字都不用改。变的只有两样：

```scala
ChainDsl.define("payroll") { c =>                    // 代付
  c.classify(... ErrorCodeMapping(                   // 错误码映射：
    successCodes    = Set("SUCCESS"),                //   成功叫 SUCCESS
    failureCodes    = Map("NO_ACCOUNT" -> Scrap)))   //   失败是"无有效账户"
  c.onFailure { r => r.when("BANK_MAINTENANCE") { RetrySameArea(1.hour) } }
}
```

骨架（六阶段队列 + 断点续跑 + 世代守卫 + 账本）全部复用。这就是噩梦六的答案：**第一次把骨架写对，之后每个业务只写血肉**。本仓库里，银行链（6 阶段）和晶圆厂链（17 阶段，见下）就是这么共用的。

## 6. 总对照表：业务问题 → 机制 → 名字 → 源码

| 业务问题 | 引擎的回答 | 机制名 | 源码入口 |
|---|---|---|---|
| 做到一半断了怎么接着做？ | 记账 + 产物快照，跳过做完的 | 断点续跑 | `resumeFromIndex` / `PhaseDone(快照)` |
| 旧进程的残留任务会不会捣乱？ | 启动编号，旧链下一边界自动退场 | 世代守卫 | `RunRegistry` / `StaleRun` |
| 超时的单子悬着怎么办？ | 三分类，可疑必须查证落定 | 三分类 | `Classification` / `ReconfirmHandler` |
| 失败重试策略怎么不发版改？ | 策略即配置：错误码 → 动作 | 重批策略 | `ReBatchPolicy` / `NextStep` |
| 监管要逐笔追溯？ | 每阶段一条事件：谁/何时/产物 | 事件溯源 | `PhaseDone` 事件 |
| 新业务不想从头写？ | 骨架复用，只换错误码和策略 | 声明式定义 | `ChainDsl.define` |

引擎**不管**的事：账本存哪（MongoDB）、怎么跟基金公司传文件（SFTP）、可疑找谁查证（查证接口）、失败项什么时候重新组批（重批调度）——全是宿主业务代码。引擎只保证一件事：**控制流永远是对的**——顺序不乱、断点准确、失败处理恰好一次、没有僵尸任务。

## 7. 两个真实宿主（同一个引擎）

| | 银行链（充值/申购基金/代付） | Fab 晶圆厂（M3.5 自愈演示） |
|---|---|---|
| 阶段 | 6 道：文件交换六工序 | 17 道：装舟→转运→上机→跑 recipe→量测→OCAP 处置→… |
| 失败处置 | 无拦截器：失败即终止，失败项进重批队列 | OCAP 拦截器：按规则返工/报废/挂起，处置完继续走 |
| 宕机恢复 | 从 PhaseDone 快照断点续跑 | 崩溃在 `Measure#9`，10 秒后从 `#9` 恢复走完全部 |

接入方式一模一样：**写阶段解释器 → 定义游标名 → 把钩子接到日志 → （可选）配失败处置器**。五步建模法见[参考手册 §2](README-zh.md)；完整业务文档见 [ChainDsl 指南](../docs/CHAINDSL_GUIDE-zh.md)。
